How do I ask my own AI about my Health Connect or Apple Health data over MCP?

Send your data with Life Dashboard Companion to Home Assistant, the Life Dashboard stack or a Postgres database you already run, put a read-only MCP server on top, and connect a model that can use MCP tools. A local model through Ollama keeps everything on your own hardware, and a cloud model such as Claude can use the same server. It works for Health Connect data from Samsung Health, Fitbit, Garmin and other apps, for Apple Health data from the iPhone app, and in Europe, where the health connectors of Claude and ChatGPT aren't available.

The app itself contains no AI and never talks to a model. This is a recipe on the receiver side: you run the MCP server, and the model reads what your receiver already stores, through a connection that can't change anything.

How it fits together

MCP is the standard way for a model to call tools, and a read-only MCP server on the receiver gives the model tools to look up your history. The iPhone app sends to the same integration and the same stack, so every route works for Apple Health data too.

Use route 1 if you send to the Life Dashboard integration, route 2 if you run the stack, and route 3 if n8n or a receiver of your own already writes to a Postgres you run.

In Europe, where the official health connectors aren't available

As of October 2026, the health connectors that Claude and ChatGPT offer themselves are for users in the US only:

  • Claude reads Apple Health and Health Connect in its iPhone and Android apps. It's in beta on Pro and Max plans and "currently limited to users in the US", according to Anthropic's help pages for Android and iPhone. On Android it needs Android 14 or later.
  • Health in ChatGPT is for logged-in users in the US aged 18 or older, on the web and iOS. It connects Apple Health on an iPhone, and the help page doesn't mention Health Connect or Android (OpenAI's help page). For the early access in January 2026, OpenAI left out the European Economic Area, Switzerland and the United Kingdom (OpenAI's announcement).

So outside the US, the EEA, the UK and Switzerland included, neither assistant reads your Health Connect or Apple Health data by itself. The route on this page doesn't depend on where you live:

  1. Your data sits in your own Home Assistant or Postgres, sent there by the app.
  2. You run a read-only MCP server on top of it.
  3. Any model that can use MCP tools reads it. That can be a local model, or Claude: Claude Desktop runs MCP servers on your own computer, and a custom connector in Claude connects from Anthropic's cloud, so that server must be reachable from the internet (Anthropic's help page).

The app doesn't come with an MCP server and doesn't talk to any AI. You run the server and decide which model may read it. With a cloud model, your questions and the query results go to its provider.

What you need

  • A model with tool support. The routes below use a local one, which Ollama runs, with a model such as qwen3 (8B or 14B) or gpt-oss:20b. Pick one without a -cloud tag: those run on Ollama's servers. An 8B model wants 16 GB of memory; 20 to 30B wants a 24 GB graphics card or a Mac with 32 GB or more.
  • A chat client that speaks MCP, such as Open WebUI or LM Studio, unless you use Home Assistant's own assistant. Ollama runs the model; the chat client makes the MCP connection.
  • History to ask about. Backfill on the Health tab sends up to a year.

Set it up

Route 1: Home Assistant with ha-mcp

The integration keeps your history in long-term statistics, with IDs like life_dashboard:<entry>_steps. With its Assist API, Home Assistant's built-in MCP server only offers current states, so it can answer “how many steps today” but not how this month compares with the last. ha-mcp, a community project, has a history tool that reads long-term statistics.

  1. In HACS, add homeassistant-ai/ha-mcp-integration as a custom repository and install it. It needs Home Assistant 2026.8 or later. Restart, then add HA-MCP Custom Component under Add integration and choose HA-MCP Server.
  2. In the HA-MCP panel in the sidebar, switch on Read Only Mode.
  3. Under Configure, turn off Remote access via webhook and set Network access to 127.0.0.1, unless a client on another machine needs it.
  4. Connect a model. Inside Home Assistant, add the Ollama integration, create a conversation agent with a tool-capable model and choose HA-MCP Server (tool search) under Control Home Assistant. Or add ha-mcp's URL in Open WebUI or LM Studio, and switch on its tool search in the HA-MCP panel. Treat that URL as an administrator password.
  5. Give the model the statistic ID, which Developer tools > Statistics lists, and ask for monthly averages with ha_get_history from its statistics.

Route 2: the stack with its read-only database role

The Life Dashboard stack stores every record in Postgres, in one table, records, with the record as JSON. Its dash views turn those records into days, nights and workouts in your time zone, so a model doesn't have to write SQL against nested JSON.

  1. Use the read-only role the stack already has, grafana_ro. It can read records, buckets and the dash views and nothing else, it's read-only by default, and its queries stop after 30 seconds. The receiver grants it again at every start, after it rebuilds the views. Its password is GRAFANA_DB_PASSWORD in .env.
  2. Add DBHub as an MCP server in docker-compose.override.yml, bound to 127.0.0.1:8081. Its config defines a read-only SQL tool and three ready-made ones that read dash.activity_days, dash.sleep_nights and dash.workouts.
  3. Start it with docker compose up -d dbhub and add http://127.0.0.1:8081/mcp in Open WebUI or LM Studio.
  4. Ask: “Using sleep_nights and workouts, how did my deep sleep compare in weeks with three or more runs against weeks with fewer?”

The stack keeps series sent per time window in its buckets table, but only its heart rate views read them. Leave Data Resolution on the Health tab at Every record, the default, for the types you want to ask about. The full recipe has the Compose service and the DBHub config.

Route 3: your own Postgres

If n8n or a receiver of your own already stores the payloads in a Postgres you run, the same pattern works there.

  1. Store records keyed on uuid as text, daily_totals as one row per date, and apply deleted_records, so a model can't count a walk twice or read a record you deleted. Store it in Postgres has the details.
  2. Create a role that can only read those tables: 
    CREATE ROLE llm_ro LOGIN PASSWORD 'change-me';
ALTER ROLE llm_ro SET default_transaction_read_only = on;
ALTER ROLE llm_ro SET statement_timeout = '30s';
GRANT CONNECT ON DATABASE health TO llm_ro;
GRANT USAGE ON SCHEMA public TO llm_ro;
GRANT SELECT ON records, daily_totals TO llm_ro;
    Use your own table and database names, and grant SELECT on every view you add later.
  3. Run DBHub in a folder of its own. Route 2's Compose service waits for the stack's receiver and needs the stack's .env, so it doesn't start without the stack; the recipe has a separate docker-compose.yml and dbhub.toml for this route.
  4. Add views with one row per day and per night. A model answers far better from those than from sleep sessions as JSON. The stack's views.sql is a template: adapt its table and column names to yours.

The stack's documentation doesn't cover running only its receiver against a Postgres you already run. The receiver does take its database from DATABASE_URL, and at every start it runs its migrations, rebuilds the dash schema and sets up the grafana_ro role, so if you try it, give it a database of its own and a user that may create roles.

What you get

  • Answers about your own history, such as monthly step averages or your sleep in weeks you trained more, from a model you choose, on your own hardware if you like.
  • Read-only access. With a read-only role or Read Only Mode, the model can't change a setting, delete a record or switch a device.

Limits

  • ha-mcp works with an administrator's access. Everyone who can talk to its conversation agent can ask about your health data, so give it its own agent, outside shared voice pipelines.
  • A question asked by voice also goes through your speech engine, which with Home Assistant Cloud isn't local.
  • The stack starts with default passwords for Grafana, the database and grafana_ro. Change them before you add another way in.
  • Types you didn't switch on, or days the phone didn't sync, aren't there to read. Screen time history only comes from Android phones.
  • Types your watch's app doesn't share with Health Connect aren't there either, and they decide which questions a model can answer. Samsung Health keeps HRV, resting heart rate and respiratory rate to itself, and Garmin Connect writes no HRV to Health Connect at all and keeps resting heart rate to itself.
  • A model isn't a doctor. It can sum your steps correctly and still draw a wrong conclusion.

FAQ

Does Life Dashboard Companion send my data to an AI?

No. The app contains no AI and never talks to a model. It sends only to the destinations you set up; the model reads from your receiver.

Can I use a cloud model such as Claude instead?

You can point one at the same server, but then your questions, every query result and the answers go to the provider. Claude Desktop can run an MCP server on your own computer. A custom connector in Claude, or a connector in another web app, connects from the provider's cloud and needs your server reachable from the internet.

Can I connect Health Connect to Claude or ChatGPT in Europe?

Not with their own health connectors. As of October 2026, Claude's Apple Health and Health Connect integration and Health in ChatGPT are only for users in the US, and ChatGPT's help page names Apple Health, not Health Connect. Your own MCP server works anywhere: the model reads the history you keep in Home Assistant or Postgres.

Is there a Health Connect MCP server?

Health Connect has no web API: it lives on the phone, so a server can't read it directly. Life Dashboard Companion sends the data to Home Assistant or Postgres, and an MCP server there, such as ha-mcp or DBHub in read-only mode, gives a model your history. That works for Samsung Health, Fitbit, Garmin and any other app that writes to Health Connect, for the types each app shares there.

Why not Home Assistant's built-in MCP server?

With the Assist API, it gives a model the current state of the entities you exposed to Assist, with no tool for history or statistics. It can answer questions about today, not about last month.
