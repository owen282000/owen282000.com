¿Cómo llevo los datos de Apple Health a n8n?

Instala Life Dashboard Companion en tu iPhone e introduce como webhook la URL de producción de un nodo Webhook de n8n. En n8n, activa la opción Raw Body del nodo Webhook, comprueba el HMAC de X-Signature en un nodo Code, responde 204 con un nodo Respond to Webhook y después guarda cada registro con su type y su uuid como clave. Todo lo que hay en Apple Health (la app Salud del iPhone) llega así a n8n, venga del iPhone, de un Apple Watch o de otra app que escriba ahí.

La app para iPhone envía el mismo payload que la app para Android, así que el workflow es el de Health Connect a n8n, y un solo workflow recibe los dos teléfonos. Esta página repite el workflow completo, con los puntos en los que un payload de iPhone es distinto. El payload en sí, los reintentos y la cola están en Apple Health a un webhook.

Qué necesitas

  • Life Dashboard Companion para iPhone con iOS 17 o posterior. {{status:ios}}
  • n8n, en n8n Cloud o autoalojado, accesible desde el iPhone. Usa HTTPS. iOS solo permite http:// sin cifrar hacia una dirección IP, un nombre .local o un nombre sin punto, y pide una vez acceso a la red local: permítelo si tu n8n está en casa.
  • Margen para peticiones grandes. n8n acepta hasta 16 MB de forma predeterminada, pero un proxy inverso delante de él también tiene que permitirlo: nginx permite 1 MB de forma predeterminada.
  • El módulo crypto en el nodo Code. n8n Cloud lo incluye. En n8n autoalojado, define NODE_FUNCTION_ALLOW_BUILTIN=crypto, en el task runner si usas uno.

El workflow de un vistazo

Webhook (POST, Raw Body)
  -> Code: check signature
  -> If: valid is true
       true  -> Respond to Webhook (204)
                  -> Code: records    -> Postgres: upsert
                  -> Code: deletions  -> Postgres: delete
       false -> Respond to Webhook (401)

La respuesta sale antes del trabajo con la base de datos: la app abandona un intento cuando la conexión lleva 10 segundos parada.

Configura el nodo Webhook

  1. Añade un nodo Webhook. Pon HTTP Method en POST y elige un Path, por ejemplo life-dashboard.
  2. Pon Respond en Using 'Respond to Webhook' Node. Con Immediately, n8n responde 200 antes de que se compruebe la firma, así que un payload con una firma incorrecta cuenta igualmente como entregado.
  3. En Options, añade Raw Body y actívalo. El nodo entrega entonces los bytes tal como llegaron en la propiedad binaria data, junto al JSON ya interpretado en body y los encabezados en headers.
  4. Publica el workflow y copia la URL de producción. La URL de prueba solo escucha mientras el editor espera un evento de prueba. Una sincronización enviada cuando nada escucha recibe un 404, y el iPhone guarda ese payload y los siguientes en su cola hasta que la URL vuelve a responder.

En la app, toca Agregar destino en la pestaña Salud, introduce la URL de producción y toca Agregar webhook. En la hoja que se abre, toca Generar en Secreto de firma HMAC, toca Copiar secreto para el paso siguiente y después toca Guardar.

Comprueba la firma en un nodo Code

El iPhone firma exactamente igual que la app para Android: X-Signature: sha256=<hex>, el HMAC-SHA256 del cuerpo en bruto con tu secreto como clave. Añade un nodo Code en JavaScript, en el modo Run Once for All Items:

const crypto = require('crypto');

// The secret as the app shows it. Use it as text: don't hex-decode it.
const SECRET = 'paste-the-secret-from-the-app';

const item = $input.first();
const raw = await this.helpers.getBinaryDataBuffer(0, 'data');
const expected = Buffer.from(
  'sha256=' + crypto.createHmac('sha256', SECRET).update(raw).digest('hex')
);
const presented = Buffer.from(item.json.headers['x-signature'] || '');
const valid = presented.length === expected.length &&
  crypto.timingSafeEqual(presented, expected);

return [{ json: { valid, payload: valid ? JSON.parse(raw.toString('utf8')) : null } }];
  • El HMAC se calcula sobre raw, los bytes que firmó la app. Calcularlo sobre body serializado de nuevo da una cadena distinta, y la comprobación falla.
  • n8n entrega los nombres de los encabezados en minúsculas, así que el encabezado es x-signature.
  • Cualquiera que pueda abrir el workflow puede leer el secreto en el código. La referencia del payload muestra la misma comprobación con un nodo Crypto, que guarda el secreto en una credencial de n8n.

Después añade un nodo If con una sola condición: el booleano {{ $json.valid }} es verdadero.

Responde antes de la parte lenta

Termina cada rama del nodo If en su propio nodo Respond to Webhook, con Respond With en No Data. En Options, pon Response Code en 204 en la rama true y en 401 en la rama false. Lo que hace el iPhone con cada respuesta:

  • 204. Cualquier 2xx cuenta como entregado. Los nodos que van después del nodo Respond to Webhook se ejecutan igualmente, con el mismo elemento.
  • 401. No se reintenta dentro de la sincronización. El payload se queda en la cola del iPhone, los siguientes esperan detrás, y salen cuando los secretos coinciden: en la siguiente sincronización o con Reintentar ahora.
  • 500. Si el workflow falla antes de que se ejecute un nodo Respond to Webhook, n8n responde 500. El iPhone lo intenta 3 veces en total, con 1 y luego 2 segundos de separación, y después guarda el payload para la siguiente sincronización.

Dos cosas cambian respecto a Android: un payload que tu workflow rechaza con 400, 413 o 422 se vuelve a ofrecer una vez al día en lugar de en cada sincronización, y un payload de más de 7 días se descarta en la siguiente entrega a la que n8n responde con un error.

Convierte el payload en filas

Después del 204, un segundo nodo Code convierte el payload en un elemento por registro. Es el mismo código que para Android:

const p = $input.first().json.payload;
if (!p || p.test) return [];

const rows = [];
for (const [type, value] of Object.entries(p)) {
  if (type === 'deleted_records' || !Array.isArray(value)) continue;
  for (const r of value) {
    if (!r || !r.uuid) continue; // daily totals and buckets carry no uuid
    rows.push({ json: {
      type,
      uuid: r.uuid,
      source: r.source ?? null,
      time: r.time ?? r.start_time ?? r.session_end_time ?? null,
      data: r,
    } });
  }
}
return rows;
  • Enviar prueba y el Ping de prueba de la configuración inicial llevan "test": true y ningún registro, así que no se ejecuta nada después de este nodo.
  • En un iPhone, el source de un registro es el nombre que Apple Health da a la app o al dispositivo que lo escribió, como Alex's Apple Watch, no un nombre de paquete. A menudo incluye el nombre del propietario.
  • El uuid de una noche de sueño viene de su fase más temprana, así que no cambia mientras la noche crece, y el upsert de más abajo sustituye la noche cuando vuelve más larga. Las fases de una noche llevan su propio uuid y su propio source dentro de data.
  • Un alimento es un único registro nutrition con todos sus nutrientes, y con su name cuando la app le dio uno.
  • Las series que pones a 1, 5 o 15 minutos o por hora en Resolución de datos llegan como intervalos sin uuid y aquí se omiten. Para este workflow, deja todos los tipos en cada registro, que es el valor predeterminado.

Guárdalo en Postgres, sin duplicados gracias al uuid

El mismo registro puede llegar más de una vez: en cada backfill, el envío de todo tu historial anterior, y otra vez desde la cola después de una entrega que iOS cortó. Usa como clave de la tabla type y uuid, ambos como text:

CREATE TABLE health_records (
  type   text NOT NULL,
  uuid   text NOT NULL,
  source text,
  time   timestamptz,
  data   jsonb NOT NULL,
  PRIMARY KEY (type, uuid)
);

Añade un nodo Postgres con la operación Execute Query:

INSERT INTO health_records (type, uuid, source, time, data)
VALUES ($1, $2, $3, $4::timestamptz, $5::jsonb)
ON CONFLICT (type, uuid) DO UPDATE
SET source = EXCLUDED.source, time = EXCLUDED.time, data = EXCLUDED.data;

En Options, añade Query Parameters con esta expresión:

{{ [ $json.type, $json.uuid, $json.source, $json.time, JSON.stringify($json.data) ] }}
  • Pasa los valores como Query Parameters, nunca como {{ }} dentro del SQL. n8n pega una expresión en el SQL como texto sin más, así que una comilla en un valor, como la de Alex's Apple Watch, rompe la consulta.
  • La clave es type más uuid, no uuid solo: un iPhone envía una misma muestra de energía activa tanto en active_calories como en total_calories.
  • Apple Health no edita un registro en el sitio. Una edición llega como el borrado del uuid antiguo y un registro nuevo, de lo que se ocupa el paso siguiente.

Aplica deleted_records

Un registro borrado en Apple Health aparece en el deleted_records de un payload posterior, con su type y su uuid. Un tercer nodo Code, también después del 204:

const p = $input.first().json.payload;
return (p?.deleted_records ?? []).map(d => ({ json: { type: d.type, uuid: d.uuid } }));

Después, un nodo Postgres con Execute Query y los Query Parameters {{ [ $json.type, $json.uuid ] }}:

DELETE FROM health_records
WHERE type = $1 AND (uuid = $2 OR starts_with(uuid, $2 || '#'));

Los uuid de un iPhone nunca llevan un #, así que para un iPhone solo importa la primera mitad; la segunda es para las muestras de frecuencia cardíaca y de temperatura de la piel de Android, y permite que un solo workflow sirva para ambos. Un uuid borrado que no tienes no borra nada, que es lo que pide la página del payload de iOS.

Hay un caso de iPhone que la consulta anterior no cubre: un borrado de sueño nombra una fase de la noche, por su uuid en stages, no la noche. Para quitar esa fase de la noche guardada, añade un segundo nodo Postgres con los mismos Query Parameters:

UPDATE health_records
SET data = jsonb_set(data, '{stages}', (
  SELECT coalesce(jsonb_agg(s), '[]'::jsonb)
  FROM jsonb_array_elements(data->'stages') AS s
  WHERE s->>'uuid' IS DISTINCT FROM $2))
WHERE type = 'sleep' AND $1 = 'sleep'
  AND data->'stages' @> jsonb_build_array(jsonb_build_object('uuid', $2::text));

El duration_seconds de la noche se queda como se envió. De un tipo que aparece en deletions_unavailable no se puede responder en esa sincronización: lanza un backfill desde la app para conciliarlo.

Si prefieres no montar el almacenamiento tú mismo, el receptor de el stack Life Dashboard elimina duplicados y borra de la misma manera, con dashboards, una API de solo lectura y un servidor MCP encima.

Google Sheets o Telegram como alternativa

Una fila por día en Google Sheets. Un nodo Code después del 204 toma los totales diarios, que Apple Health cuenta como lo hace la app Salud, así que un paseo registrado por el iPhone y por el reloj cuenta una sola vez:

const p = $input.first().json.payload;
return (p?.daily_totals ?? []).map(d => ({ json: d }));

Después, un nodo Google Sheets con Append or Update Row, una hoja con las columnas date, steps, distance_meters, active_calories y total_calories, y date como la columna de coincidencia. Cada payload lleva hoy y los dos días anteriores, así que la fila de hoy se actualiza con cada sincronización. En un iPhone, total_calories solo llega en los días con energía en reposo, que un iPhone sin Apple Watch no suele registrar.

Un mensaje de Telegram por cada peso nuevo. Después del nodo de registros, un nodo Filter conserva los elementos en los que {{ $json.type }} es weight. Un nodo Remove Duplicates con Remove Items Processed in Previous Executions, Keep Items Where en Value Is New y {{ $json.uuid }} como el valor con el que detectar duplicados evita un segundo mensaje cuando el mismo pesaje vuelve a llegar en un backfill. Después, un nodo Telegram con Send Message y el texto Weight: {{ $json.data.kilograms }} kg.

Un iPhone y un teléfono Android en un solo workflow

  • El source de nivel superior es healthkit_ios desde un iPhone y health_connect desde Android.
  • La variabilidad de la frecuencia cardíaca (HRV) es SDNN desde un iPhone y RMSSD desde Android, bajo la misma clave. Guarda el source de nivel superior con cada registro para que las dos queden separadas.
  • El type de un entrenamiento es un nombre como running desde un iPhone, y el número de Health Connect como cadena, por ejemplo "56", desde Android.
  • Las fases del sueño de un iPhone incluyen in_bed, el tiempo en la cama alrededor de las fases.
  • El tiempo de pantalla solo viene de Android, como un payload propio.

Los pasos de registros, upsert y borrado de esta página vienen del workflow de Health Connect a n8n. Los nodos Code y el SQL se comprobaron aquí con un payload de iPhone en Node.js y Postgres, no en un n8n en marcha con un iPhone enviándole datos, así que pruébalo con Enviar prueba y Sincronizar ahora antes de confiar en él.

Limitaciones

  • n8n no puede pedirle al iPhone un intervalo de fechas. Inicia un backfill en el iPhone, desde 30 días hasta Todo el historial, con Enviar historial en Qué enviar.
  • iOS decide cuándo se ejecuta la app en segundo plano, así que las sincronizaciones pueden llegar más tarde de lo que dice el horario. Para una hora exacta, una automatización de Atajos ejecuta Sincronizar datos de salud.
  • Como el 204 sale primero, dos payloads pueden guardarse al mismo tiempo. Los payloads llevan un sequence que solo aumenta; úsalo cuando el orden importe, por ejemplo para daily_totals.

FAQ

¿Es distinto el workflow del de Android?

Solo en los detalles de esta página. El nodo Webhook, la comprobación de la firma, las respuestas y el upsert son los mismos, así que un solo workflow puede recibir los dos teléfonos. El paso adicional es el borrado de una fase del sueño, que solo envía un iPhone.

¿Funciona en n8n Cloud?

Sí. La URL de producción de un workflow publicado es HTTPS pública, y n8n Cloud ofrece el módulo crypto al nodo Code. n8n autoalojado necesita NODE_FUNCTION_ALLOW_BUILTIN=crypto para el mismo código.

¿Por qué falla la comprobación de la firma en todas las peticiones?

Normalmente por una de tres cosas: Raw Body está desactivado, así que no hay ningún data binario sobre el que calcular el hash; el HMAC se calcula sobre el body interpretado en lugar de sobre los bytes en bruto; o el secreto de n8n es distinto del de la app. Copia el secreto otra vez y úsalo como texto sin más.

¿Llegan a n8n los datos del Apple Watch?

Sí. El reloj escribe en Apple Health en el iPhone, y la app los envía una vez que el reloj se ha sincronizado con el iPhone. Apple Watch en Home Assistant enumera lo que suele registrar un reloj.

¿Puedo ver un payload antes de montar el workflow?

Sí. Vista previa del payload, en Qué enviar dentro de la app, muestra los últimos 7 días como un payload. En n8n, la URL de prueba con Listen for Test Event muestra una petición real en el editor.
