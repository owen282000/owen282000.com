Como levar os dados do Apple Health para o n8n?

Instale o app Life Dashboard no iPhone e informe a URL de produção de um nó Webhook do n8n como o webhook dele. No n8n, ative a opção Raw Body do nó Webhook, verifique o HMAC do X-Signature em um nó Code, responda 204 com um nó Respond to Webhook e depois armazene cada registro usando type e uuid como chave. Tudo o que está no Apple Health (o app Saúde do iPhone) chega ao n8n assim, venha do iPhone, de um Apple Watch ou de outro app que grave ali.

O app do iPhone envia o mesmo payload do app para Android, então o workflow é o de Conexão Saúde (Health Connect) para o n8n, e um único workflow atende os dois celulares. Esta página traz o workflow inteiro de novo, com os pontos em que o payload de um iPhone difere. O payload em si, as novas tentativas e a fila estão em Apple Health para um webhook.

O que você precisa

  • O Life Dashboard para iPhone no iOS 17 ou mais recente. {{status:ios}}
  • O n8n, no n8n Cloud ou auto-hospedado, acessível a partir do iPhone. Use HTTPS. O iOS só permite http:// sem criptografia para um endereço IP, um nome .local ou um nome sem ponto, e pergunta uma vez sobre o acesso à rede local: permita, se o n8n fica em casa.
  • Espaço para requisições grandes. O n8n aceita até 16 MB por padrão, mas um proxy reverso na frente dele também precisa permitir isso: o nginx permite 1 MB por padrão.
  • O módulo crypto no nó Code. O n8n Cloud já o oferece. No n8n auto-hospedado, defina NODE_FUNCTION_ALLOW_BUILTIN=crypto, no task runner se você usa um.

O workflow em resumo

Webhook (POST, Raw Body)
  -> Code: check signature
  -> If: valid is true
       true  -> Respond to Webhook (204)
                  -> Code: records    -> Postgres: upsert
                  -> Code: deletions  -> Postgres: delete
       false -> Respond to Webhook (401)

A resposta sai antes do trabalho no banco de dados: o app desiste de uma tentativa quando a conexão fica parada por 10 segundos.

Configure o nó Webhook

  1. Adicione um nó Webhook. Defina HTTP Method como POST e escolha um Path, como life-dashboard.
  2. Defina Respond como Using 'Respond to Webhook' Node. Com Immediately, o n8n responde 200 antes de a verificação da assinatura rodar, então um payload com assinatura errada ainda conta como entregue.
  3. Em Options, adicione Raw Body e ative. O nó passa então a entregar os bytes como chegaram na propriedade binária data, ao lado do JSON interpretado em body e dos cabeçalhos em headers.
  4. Publique o workflow e copie a URL de produção. A URL de teste só escuta enquanto o editor espera um evento de teste. Uma sincronização enviada quando nada está escutando recebe um 404, e o iPhone guarda esse payload e os seguintes na fila até a URL voltar a responder.

No app, toque em Adicionar destino na aba Saúde, informe a URL de produção e toque em Adicionar webhook. Na tela que abre, toque em Gerar em Segredo de assinatura HMAC, toque em Copiar segredo para o próximo passo e depois em Salvar.

Verifique a assinatura em um nó Code

O iPhone assina exatamente como o app para Android: X-Signature: sha256=<hex>, o HMAC-SHA256 do corpo bruto com o seu segredo como chave. Adicione um nó Code em JavaScript, no modo Run Once for All Items:

const crypto = require('crypto');

// The secret as the app shows it. Use it as text: don't hex-decode it.
const SECRET = 'paste-the-secret-from-the-app';

const item = $input.first();
const raw = await this.helpers.getBinaryDataBuffer(0, 'data');
const expected = Buffer.from(
  'sha256=' + crypto.createHmac('sha256', SECRET).update(raw).digest('hex')
);
const presented = Buffer.from(item.json.headers['x-signature'] || '');
const valid = presented.length === expected.length &&
  crypto.timingSafeEqual(presented, expected);

return [{ json: { valid, payload: valid ? JSON.parse(raw.toString('utf8')) : null } }];
  • O HMAC é calculado sobre raw, os bytes que o app assinou. Calcular sobre body serializado de novo dá uma string diferente, e a verificação falha.
  • O n8n entrega os nomes dos cabeçalhos em minúsculas, então o cabeçalho é x-signature.
  • Quem consegue abrir o workflow consegue ler o segredo no código. A referência do payload mostra a mesma verificação com um nó Crypto, que guarda o segredo em uma credencial do n8n.

Depois adicione um nó If com uma condição: o booleano {{ $json.valid }} é verdadeiro.

Responda antes da parte lenta

Termine cada ramo do nó If em seu próprio nó Respond to Webhook, com Respond With definido como No Data. Em Options, defina Response Code como 204 no ramo true e 401 no ramo false. O que o iPhone faz com cada resposta:

  • 204. Qualquer 2xx conta como entregue. Os nós depois do nó Respond to Webhook continuam rodando, com o mesmo item.
  • 401. Não há nova tentativa dentro da sincronização. O payload fica na fila do iPhone, os seguintes esperam atrás dele, e todos saem quando os segredos batem: na sincronização seguinte, ou com Tentar agora.
  • 500. Se o workflow falha antes de um nó Respond to Webhook rodar, o n8n responde 500. O iPhone tenta 3 vezes ao todo, com 1 e depois 2 segundos de intervalo, e então guarda o payload para a sincronização seguinte.

Duas coisas são diferentes do Android: um payload que o seu workflow recusa com 400, 413 ou 422 é oferecido de novo uma vez por dia, e não a cada sincronização, e um payload com mais de 7 dias é descartado na entrega seguinte a que o n8n responder com erro.

Transforme o payload em linhas

Depois do 204, um segundo nó Code transforma o payload em um item por registro. É o mesmo código do Android:

const p = $input.first().json.payload;
if (!p || p.test) return [];

const rows = [];
for (const [type, value] of Object.entries(p)) {
  if (type === 'deleted_records' || !Array.isArray(value)) continue;
  for (const r of value) {
    if (!r || !r.uuid) continue; // daily totals and buckets carry no uuid
    rows.push({ json: {
      type,
      uuid: r.uuid,
      source: r.source ?? null,
      time: r.time ?? r.start_time ?? r.session_end_time ?? null,
      data: r,
    } });
  }
}
return rows;
  • Enviar teste e o Ping de teste da configuração inicial trazem "test": true e nenhum registro, então nada depois deste nó roda.
  • Em um iPhone, o source de um registro é o nome que o Apple Health dá ao app ou aparelho que o gravou, como Alex's Apple Watch, e não um nome de pacote. Muitas vezes ele inclui o nome do dono.
  • O uuid de uma noite de sono vem da fase mais antiga dela, então continua o mesmo enquanto a noite cresce, e o upsert abaixo substitui a noite quando ela volta mais longa. As fases de uma noite trazem seus próprios uuid e source em data.
  • Um alimento é um único registro nutrition com todos os nutrientes dentro, e com o name dele quando o app informou um.
  • As séries que você definiu como 1, 5 ou 15 minutos ou por hora em Resolução dos dados chegam como intervalos agregados sem uuid e são ignoradas aqui. Para este workflow, deixe todos os tipos em todos os registros, que é o padrão.

Armazene no Postgres, sem duplicatas pelo uuid

O mesmo registro pode chegar mais de uma vez: em cada backfill (o envio de todo o histórico de uma vez), e de novo a partir da fila depois de uma entrega que o iOS interrompeu. Use type e uuid como chave da tabela, os dois como text:

CREATE TABLE health_records (
  type   text NOT NULL,
  uuid   text NOT NULL,
  source text,
  time   timestamptz,
  data   jsonb NOT NULL,
  PRIMARY KEY (type, uuid)
);

Adicione um nó Postgres com a operação Execute Query:

INSERT INTO health_records (type, uuid, source, time, data)
VALUES ($1, $2, $3, $4::timestamptz, $5::jsonb)
ON CONFLICT (type, uuid) DO UPDATE
SET source = EXCLUDED.source, time = EXCLUDED.time, data = EXCLUDED.data;

Em Options, adicione Query Parameters com esta expressão:

{{ [ $json.type, $json.uuid, $json.source, $json.time, JSON.stringify($json.data) ] }}
  • Passe os valores como Query Parameters, nunca como {{ }} dentro do SQL. O n8n cola uma expressão no SQL como texto puro, então uma aspa em um valor, como a de Alex's Apple Watch, quebra a consulta.
  • A chave é type mais uuid, não só uuid: um iPhone envia uma mesma amostra de energia ativa tanto em active_calories quanto em total_calories.
  • O Apple Health não edita um registro no lugar. Uma edição chega como a exclusão do uuid antigo e um registro novo, e o próximo passo cuida disso.

Aplique deleted_records

Um registro apagado no Apple Health é citado no deleted_records de um payload posterior, com seu type e seu uuid. Um terceiro nó Code, também depois do 204:

const p = $input.first().json.payload;
return (p?.deleted_records ?? []).map(d => ({ json: { type: d.type, uuid: d.uuid } }));

Depois, um nó Postgres com Execute Query e os Query Parameters {{ [ $json.type, $json.uuid ] }}:

DELETE FROM health_records
WHERE type = $1 AND (uuid = $2 OR starts_with(uuid, $2 || '#'));

Os uuids de um iPhone nunca têm um #, então para um iPhone só a primeira metade importa; a segunda metade serve para as amostras de frequência cardíaca e de temperatura da pele do Android, e permite que um único workflow atenda os dois. Um uuid apagado que você não tem não apaga nada, que é o que a página do payload do iOS pede.

Há um caso do iPhone que a consulta acima não cobre: uma exclusão de sono cita uma fase da noite, pelo uuid dela em stages, e não a noite. Para remover essa fase da noite armazenada, adicione um segundo nó Postgres com os mesmos Query Parameters:

UPDATE health_records
SET data = jsonb_set(data, '{stages}', (
  SELECT coalesce(jsonb_agg(s), '[]'::jsonb)
  FROM jsonb_array_elements(data->'stages') AS s
  WHERE s->>'uuid' IS DISTINCT FROM $2))
WHERE type = 'sleep' AND $1 = 'sleep'
  AND data->'stages' @> jsonb_build_array(jsonb_build_object('uuid', $2::text));

O duration_seconds da noite continua como foi enviado. Por um tipo listado em deletions_unavailable o payload não pode responder naquela sincronização: rode um backfill pelo app para acertar esse tipo.

Se você prefere não montar o armazenamento por conta própria, o receptor da stack Life Dashboard elimina duplicatas e apaga do mesmo jeito, com dashboards, uma API somente leitura e um servidor MCP por cima.

Google Sheets ou Telegram no lugar

Uma linha por dia no Google Sheets. Um nó Code depois do 204 pega os totais diários, que o Apple Health conta do jeito que o app Saúde conta, então uma caminhada registrada pelo iPhone e pelo Watch conta uma vez:

const p = $input.first().json.payload;
return (p?.daily_totals ?? []).map(d => ({ json: d }));

Depois, um nó Google Sheets com Append or Update Row, uma planilha com as colunas date, steps, distance_meters, active_calories e total_calories, e date como a coluna de correspondência. Todo payload traz hoje e os dois dias anteriores, então a linha de hoje é atualizada a cada sincronização. Em um iPhone, total_calories só vem nos dias com energia em repouso, que um iPhone sem Apple Watch normalmente não registra.

Uma mensagem no Telegram a cada peso novo. Depois do nó dos registros, um nó Filter mantém os itens em que {{ $json.type }} é weight. Um nó Remove Duplicates com Remove Items Processed in Previous Executions, Keep Items Where definido como Value Is New e {{ $json.uuid }} como o valor para comparar evita uma segunda mensagem quando a mesma pesagem volta em um backfill. Depois, um nó Telegram com Send Message e o texto Weight: {{ $json.data.kilograms }} kg.

Um iPhone e um celular Android no mesmo workflow

  • O source do nível superior é healthkit_ios em um iPhone e health_connect no Android.
  • A variabilidade da frequência cardíaca é SDNN em um iPhone e RMSSD no Android, na mesma chave. Guarde o source do nível superior com cada registro para manter os dois separados.
  • O type de um treino é um nome como running em um iPhone, e o número do Conexão Saúde como string, como "56", no Android.
  • As fases do sono de um iPhone incluem in_bed, o tempo na cama em volta das fases.
  • O tempo de tela só vem do Android, como um payload próprio.

Os passos de registros, upsert e exclusão desta página vêm do workflow de Conexão Saúde para o n8n. Os nós Code e o SQL foram conferidos aqui com um payload de iPhone em Node.js e Postgres, não em um n8n rodando com um iPhone enviando para ele, então teste com Enviar teste e Sincronizar agora antes de confiar nele.

Limites

  • O n8n não consegue pedir um intervalo de datas ao iPhone. Comece um backfill no iPhone, de 30 dias até Todo o histórico, com Enviar histórico em O que enviar.
  • O iOS decide quando o app roda em segundo plano, então as sincronizações podem chegar depois do que a agenda diz. Para um horário exato, uma automação do Atalhos executa Sincronizar dados de saúde.
  • Como o 204 sai primeiro, dois payloads podem ser armazenados ao mesmo tempo. Os payloads trazem um sequence que só aumenta; use esse campo quando a ordem importa, como em daily_totals.

FAQ

O workflow é diferente do workflow do Android?

Só nos detalhes desta página. O nó Webhook, a verificação da assinatura, as respostas e o upsert são os mesmos, então um único workflow pode atender os dois celulares. O passo a mais é a exclusão de uma fase do sono, que só um iPhone envia.

Isso funciona no n8n Cloud?

Sim. A URL de produção de um workflow publicado é HTTPS público, e o n8n Cloud oferece o módulo crypto ao nó Code. O n8n auto-hospedado precisa de NODE_FUNCTION_ALLOW_BUILTIN=crypto para o mesmo código.

Por que a verificação da assinatura falha em toda requisição?

Normalmente é uma de três coisas: Raw Body está desativado, então não há data binário para o hash; o HMAC é calculado sobre o body interpretado em vez dos bytes brutos; ou o segredo no n8n é diferente do segredo no app. Copie o segredo de novo e use como texto puro.

Os dados do Apple Watch chegam ao n8n?

Sim. O relógio grava no Apple Health do iPhone, e o app envia os dados adiante depois que o relógio sincroniza com o iPhone. Apple Watch no Home Assistant lista o que um relógio costuma registrar.

Dá para ver um payload antes de montar o workflow?

Sim. Prévia do payload em O que enviar, no app, mostra os últimos 7 dias como um payload. No n8n, a URL de teste com Listen for Test Event mostra uma requisição real no editor.
