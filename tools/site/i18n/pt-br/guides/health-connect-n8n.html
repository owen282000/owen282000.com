Como levar os dados do Conexão Saúde (Health Connect) para o n8n?

Instale o Life Dashboard Companion, um app Android de código aberto, e informe a URL de produção de um nó Webhook do n8n como o webhook dele. No n8n, ative a opção Raw Body do nó Webhook, confira o HMAC do X-Signature em um nó Code, responda 204 com um nó Respond to Webhook e depois grave cada registro usando o type e o uuid como chave. Os dados do Samsung Health, do Garmin Connect, do Google Health, do Oura e do Withings chegam ao n8n desse jeito, porque esses apps os gravam no Conexão Saúde (Health Connect) no celular.

O app para iPhone envia os dados do Apple Health no mesmo formato, então um único workflow atende os dois celulares. Esta página trata do lado do n8n. O payload em si, as novas tentativas e a fila de saída estão em Conexão Saúde para um webhook.

O que você precisa

  • O Life Dashboard Companion para Android em um Android 9 ou mais recente com o Conexão Saúde. {{status:android}}
  • Ou o app para iPhone com iOS 17 ou mais recente. {{status:ios}}
  • O n8n, no n8n Cloud ou no seu próprio servidor, acessível a partir do celular. Use HTTPS. HTTP sem criptografia na sua própria rede exige Permitir webhooks com HTTP sem criptografia em Mais > Avançado no app para Android; o app para iPhone só permite HTTP sem criptografia para um endereço IP, um nome .local ou um nome sem ponto.
  • Espaço para requisições grandes. Permita pelo menos 10 MB por requisição. O n8n aceita até 16 MB por padrão, mas um proxy reverso na frente dele também precisa permitir isso: o nginx permite 1 MB por padrão.
  • O módulo crypto no nó Code. O n8n Cloud já o oferece. No n8n auto-hospedado, defina NODE_FUNCTION_ALLOW_BUILTIN=crypto, no task runner se você usa um.

O workflow em resumo

Webhook (POST, Raw Body)
  -> Code: check signature
  -> If: valid is true
       true  -> Respond to Webhook (204)
                  -> Code: records    -> Postgres: upsert
                  -> Code: deletions  -> Postgres: delete
       false -> Respond to Webhook (401)

A resposta sai antes do trabalho no banco de dados, porque o app espera no máximo 10 segundos por uma resposta.

Configure o nó Webhook

  1. Adicione um nó Webhook. Defina HTTP Method como POST e escolha um Path, como life-dashboard.
  2. Defina Respond como Using 'Respond to Webhook' Node. Com Immediately, o n8n responde 200 antes de a verificação da assinatura rodar, então um payload com assinatura errada ainda conta como entregue.
  3. Em Options, adicione Raw Body e ative. O nó passa a entregar os bytes como chegaram na propriedade binária data, ao lado do JSON interpretado em body e dos cabeçalhos em headers.
  4. Publique o workflow e copie a URL de produção. A URL de teste só escuta enquanto o editor espera um evento de teste, e a URL de produção só funciona enquanto o workflow está publicado. Uma sincronização enviada em outro momento recebe um 404, e o app guarda esse payload e os seguintes até a URL voltar a responder.

No app, toque em Adicionar destino (se ainda não houver nada configurado, Usar seu próprio servidor) na aba Saúde, cole a URL de produção em URL do webhook e toque em Adicionar webhook. Na página que abre, toque em Gerar em Segredo de assinatura HMAC (opcional), copie o segredo com Copiar segredo para o próximo passo e toque em Salvar.

Confira a assinatura em um nó Code

Toda requisição traz X-Signature: sha256=<hex>, o HMAC-SHA256 do corpo bruto com o seu segredo como chave. Adicione um nó Code em JavaScript, no modo Run Once for All Items:

const crypto = require('crypto');

// The secret as the app shows it. Use it as text: don't hex-decode it.
const SECRET = 'paste-the-secret-from-the-app';

const item = $input.first();
const raw = await this.helpers.getBinaryDataBuffer(0, 'data');
const expected = Buffer.from(
  'sha256=' + crypto.createHmac('sha256', SECRET).update(raw).digest('hex')
);
const presented = Buffer.from(item.json.headers['x-signature'] || '');
const valid = presented.length === expected.length &&
  crypto.timingSafeEqual(presented, expected);

return [{ json: { valid, payload: valid ? JSON.parse(raw.toString('utf8')) : null } }];
  • O HMAC é calculado sobre raw, os bytes que o app assinou. Calculá-lo sobre o body serializado de novo dá uma string diferente, e a verificação falha.
  • O n8n entrega os nomes dos cabeçalhos em minúsculas, então o cabeçalho é x-signature.
  • timingSafeEqual compara em tempo constante e lança um erro quando as entradas têm tamanhos diferentes, por isso a checagem do tamanho vem antes.
  • Quem consegue abrir o workflow consegue ler o segredo no código. Se isso for um problema, a referência do payload mostra a mesma verificação com um nó Crypto, que guarda o segredo em uma credencial do n8n.

Depois adicione um nó If com uma condição: o booleano {{ $json.valid }} é verdadeiro.

Responda antes da parte lenta

Termine cada ramo do nó If em um nó Respond to Webhook próprio, com Respond With definido como No Data. Em Options, defina Response Code como 204 no ramo verdadeiro e 401 no ramo falso.

  • 204. O app conta qualquer 2xx como entregue. Os nós depois do nó Respond to Webhook continuam rodando, com o mesmo item.
  • 401. O app não tenta de novo. Ele guarda o payload, e os seguintes, na fila de saída e os entrega quando os segredos baterem.
  • 500. Se o workflow falhar antes de um nó Respond to Webhook rodar, o n8n responde 500. O app tenta 3 vezes ao todo e depois guarda o payload para a próxima sincronização.

Transforme o payload em linhas

Depois do 204, um segundo nó Code transforma o payload em um item por registro:

const p = $input.first().json.payload;
if (!p || p.test) return [];

const rows = [];
for (const [type, value] of Object.entries(p)) {
  if (type === 'deleted_records' || !Array.isArray(value)) continue;
  for (const r of value) {
    if (!r || !r.uuid) continue; // daily totals and buckets carry no uuid
    rows.push({ json: {
      type,
      uuid: r.uuid,
      source: r.source ?? null,
      time: r.time ?? r.start_time ?? r.session_end_time ?? null,
      data: r,
    } });
  }
}
return rows;

Um Enviar teste do app não gera linhas, então nada depois desse nó roda. As séries que você definiu como 1, 5 ou 15 minutos ou por hora em Resolução dos dados chegam como intervalos sem uuid e são ignoradas aqui: para este workflow, deixe a Resolução dos dados em todos os registros, ou guarde os intervalos em uma tabela própria, com a série e o bucket_start como chave.

Guarde no Postgres, sem duplicatas pelo uuid

O mesmo registro pode chegar mais de uma vez: depois de uma nova tentativa, quando a fonte o edita, e em todo backfill (o envio de todo o histórico de uma vez). Use type e uuid como chave da tabela, os dois como text:

CREATE TABLE health_records (
  type   text NOT NULL,
  uuid   text NOT NULL,
  source text,
  time   timestamptz,
  data   jsonb NOT NULL,
  PRIMARY KEY (type, uuid)
);

Adicione um nó Postgres com a operação Execute Query:

INSERT INTO health_records (type, uuid, source, time, data)
VALUES ($1, $2, $3, $4::timestamptz, $5::jsonb)
ON CONFLICT (type, uuid) DO UPDATE
SET source = EXCLUDED.source, time = EXCLUDED.time, data = EXCLUDED.data;

Em Options, adicione Query Parameters com esta expressão:

{{ [ $json.type, $json.uuid, $json.source, $json.time, JSON.stringify($json.data) ] }}
  • Passe os valores como Query Parameters, nunca como {{ }} dentro do SQL. O n8n cola uma expressão no SQL como texto puro, então uma aspa em um valor quebra a consulta.
  • A chave é type mais uuid, não o uuid sozinho. As amostras de frequência cardíaca e de temperatura da pele têm um uuid no formato <record id>#<epoch ms>, e um iPhone envia uma mesma amostra de energia ativa tanto em active_calories quanto em total_calories.
  • No Android, um registro editado chega com o mesmo uuid e valores novos, e o upsert substitui a linha antiga. O Apple Health não edita no lugar: uma edição chega como uma exclusão e um registro novo.

Aplique o deleted_records

Um registro excluído no Conexão Saúde ou no Apple Health é citado em deleted_records em um payload posterior, com o type e o uuid. Um terceiro nó Code, também depois do 204:

const p = $input.first().json.payload;
return (p?.deleted_records ?? []).map(d => ({ json: { type: d.type, uuid: d.uuid } }));

Depois, um nó Postgres com Execute Query e os Query Parameters {{ [ $json.type, $json.uuid ] }}:

DELETE FROM health_records
WHERE type = $1 AND (uuid = $2 OR starts_with(uuid, $2 || '#'));

A segunda metade exclui as amostras de um registro de frequência cardíaca ou de temperatura da pele vindo do Android. No iPhone, a exclusão de um sono cita uma fase da noite, não a noite inteira, então esta consulta deixa a noite no lugar. Um tipo listado em deletions_unavailable não pôde ser garantido naquela sincronização: rode um backfill pelo app para acertá-lo.

Com os registros no Postgres, um modelo pode lê-los por meio de um papel somente leitura e de um servidor MCP: dados do Conexão Saúde via MCP mostra esse caminho. Se você prefere não construir o armazenamento, o receptor da stack Life Dashboard remove duplicatas e exclui do mesmo jeito, com dashboards, uma API somente leitura e um servidor MCP por cima.

Google Sheets ou Telegram no lugar

Uma linha por dia no Google Sheets. Um nó Code depois do 204 pega os totais diários, que contam uma caminhada uma vez só, mesmo quando o celular e o relógio a registraram:

const p = $input.first().json.payload;
return (p?.daily_totals ?? []).map(d => ({ json: d }));

Depois, um nó Google Sheets com Append or Update Row, uma planilha com as colunas date, steps, distance_meters, active_calories e total_calories, e date como a coluna de correspondência. A linha de hoje é um acumulado e se atualiza a cada sincronização. Um campo fica de fora em um dia sem dados daquele tipo.

Uma mensagem no Telegram a cada peso novo. Depois do nó de registros, um nó Filter mantém os itens em que {{ $json.type }} é weight. Um nó Remove Duplicates com Remove Items Processed in Previous Executions, Keep Items Where definido como Value Is New e {{ $json.uuid }} como o valor de comparação evita uma segunda mensagem quando a mesma pesagem volta em um backfill. Depois, um nó Telegram com Send Message e o texto Weight: {{ $json.data.kilograms }} kg.

Samsung Health, Garmin e Apple Health em um só workflow

  • O source de cada registro é o nome do pacote do app que o gravou, como com.sec.android.app.shealth para o Samsung Health, com.garmin.android.apps.connectmobile para o Garmin Connect ou com.fitbit.FitbitMobile para o Google Health. Filtre por ele para encaminhar uma marca.
  • O source do nível superior é health_connect no Android e healthkit_ios no iPhone. No iPhone, o source de um registro é o nome que o Apple Health dá ao app ou ao dispositivo.
  • A variabilidade da frequência cardíaca é RMSSD no Android e SDNN no iPhone, na mesma chave. Se os dois celulares enviam para este workflow, guarde o source do nível superior com cada registro, para que as duas fiquem separadas.
  • Quais tipos cada app grava, e quais ele guarda para si, está em tipos de dados do Conexão Saúde, app por app.

Limites

  • O n8n não consegue pedir um intervalo de datas ao celular. Comece um backfill no celular, de 30 dias até Todo o histórico, em Enviar histórico, dentro de O que enviar na aba Saúde.
  • Como o 204 sai primeiro, dois payloads podem ser gravados ao mesmo tempo. Os payloads também trazem um sequence que só aumenta: Conexão Saúde para um webhook explica como usá-lo quando a ordem importa, como no caso de daily_totals.
  • O tempo de tela chega como um payload próprio com "source": "screen_time", vindo das URLs da aba Tempo de tela. Ele não tem uuids de registro, então o nó de registros acima o ignora.

FAQ

Isso funciona no n8n Cloud?

Sim. A URL de produção de um workflow publicado é HTTPS público, e o n8n Cloud oferece o módulo crypto ao nó Code. O n8n auto-hospedado precisa de NODE_FUNCTION_ALLOW_BUILTIN=crypto para o mesmo código.

Por que a verificação da assinatura falha em toda requisição?

Em geral é uma de três coisas: o Raw Body está desativado, então não existe o binário data para calcular o hash; o HMAC é calculado sobre o body interpretado em vez dos bytes brutos; ou o segredo no n8n é diferente do que está no app. Copie o segredo de novo e use-o como texto puro.

Posso dispensar a assinatura?

Sim. Sem um segredo, o app não envia o X-Signature. Proteja a URL de outro jeito, por exemplo com Header Auth no nó Webhook e o mesmo cabeçalho em Cabeçalhos na página do endereço no app.

Os dados do Samsung Health chegam ao n8n?

Sim, desde que o Samsung Health os compartilhe com o Conexão Saúde: passos, exercícios, sono com fases, frequência cardíaca, pressão arterial, peso e mais. O Samsung Health não compartilha a variabilidade da frequência cardíaca nem a frequência cardíaca em repouso com o Conexão Saúde, então esses dados não chegam.

Dá para ver um payload antes de montar o workflow?

Sim. Prévia do payload, em O que enviar na aba Saúde do app, mostra o que a próxima sincronização enviaria. No n8n, a URL de teste com Listen for Test Event mostra uma requisição real no editor.
