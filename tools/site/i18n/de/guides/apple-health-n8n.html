Wie bekomme ich Apple-Health-Daten in n8n?

Installiere die Life-Dashboard-App auf deinem iPhone und trag die Production-URL eines Webhook-Nodes in n8n als Webhook ein. In n8n schaltest du im Webhook-Node die Option Raw Body ein, prüfst den HMAC aus X-Signature in einem Code-Node, antwortest mit einem Node Respond to Webhook mit 204 und speicherst danach jeden Datensatz mit type und uuid als Schlüssel. Alles, was in Apple Health liegt, erreicht n8n auf diesem Weg: vom iPhone, von einer Apple Watch oder von einer anderen App, die dort hineinschreibt.

Die iPhone-App sendet den Payload der Android-App. Der Workflow ist also der aus Health Connect mit n8n, und ein Workflow nimmt beide Telefone an. Diese Seite zeigt den ganzen Workflow noch einmal, mit den Stellen, an denen der Payload eines iPhones abweicht. Der Payload selbst, Wiederholungen und die Warteschlange stehen in Apple-Health-Daten per Webhook exportieren.

Was du brauchst

  • Life Dashboard für iPhone auf iOS 17 oder neuer. {{status:ios}}
  • n8n, in der n8n Cloud oder selbst gehostet, vom iPhone aus erreichbar. Nimm HTTPS. iOS erlaubt unverschlüsseltes http:// nur zu einer IP-Adresse, zu einem .local-Namen oder zu einem Namen ohne Punkt und fragt einmal nach dem Zugriff auf das lokale Netzwerk: Erlaube ihn für ein n8n bei dir zu Hause.
  • Platz für große Anfragen. n8n nimmt standardmäßig bis zu 16 MB an, aber ein Reverse Proxy davor muss das ebenfalls erlauben: nginx erlaubt standardmäßig 1 MB.
  • Das Modul crypto im Code-Node. Die n8n Cloud stellt es bereit. In selbst gehostetem n8n setzt du NODE_FUNCTION_ALLOW_BUILTIN=crypto, und zwar am Task Runner, falls du einen betreibst.

Der Workflow im Überblick

Webhook (POST, Raw Body)
  -> Code: check signature
  -> If: valid is true
       true  -> Respond to Webhook (204)
                  -> Code: records    -> Postgres: upsert
                  -> Code: deletions  -> Postgres: delete
       false -> Respond to Webhook (401)

Die Antwort geht vor der Arbeit an der Datenbank raus: Die App bricht einen Versuch ab, sobald die Verbindung 10 Sekunden lang stillsteht.

Den Webhook-Node einrichten

  1. Füge einen Node Webhook hinzu. Stell HTTP Method auf POST und wähle einen Path, etwa life-dashboard.
  2. Stell Respond auf Using 'Respond to Webhook' Node. Mit Immediately antwortet n8n mit 200, bevor die Signaturprüfung läuft. Ein Payload mit falscher Signatur würde dann trotzdem als zugestellt gelten.
  3. Füge unter Options die Option Raw Body hinzu und schalte sie ein. Der Node gibt die Bytes dann so, wie sie angekommen sind, in der Binäreigenschaft data aus, neben dem geparsten JSON in body und den Headern in headers.
  4. Veröffentliche den Workflow und kopiere die Production-URL. Die Test-URL hört nur zu, solange der Editor auf ein Test-Event wartet. Eine Synchronisierung, während nichts zuhört, bekommt eine 404, und das iPhone behält diesen Payload und die folgenden in seiner Warteschlange, bis die URL wieder antwortet.

Tippe in der App auf dem Tab Gesundheit auf Ziel hinzufügen, trag die Production-URL ein und tippe auf Webhook hinzufügen. Auf dem Blatt, das sich öffnet, tippst du unter HMAC-Signaturgeheimnis auf Erzeugen, für den nächsten Schritt auf Geheimnis kopieren und dann auf Sichern.

Die Signatur in einem Code-Node prüfen

Das iPhone signiert genau wie die Android-App: X-Signature: sha256=<hex>, der HMAC-SHA256 über den rohen Body mit deinem Schlüssel. Füge einen Node Code in JavaScript hinzu, im Modus Run Once for All Items:

const crypto = require('crypto');

// The secret as the app shows it. Use it as text: don't hex-decode it.
const SECRET = 'paste-the-secret-from-the-app';

const item = $input.first();
const raw = await this.helpers.getBinaryDataBuffer(0, 'data');
const expected = Buffer.from(
  'sha256=' + crypto.createHmac('sha256', SECRET).update(raw).digest('hex')
);
const presented = Buffer.from(item.json.headers['x-signature'] || '');
const valid = presented.length === expected.length &&
  crypto.timingSafeEqual(presented, expected);

return [{ json: { valid, payload: valid ? JSON.parse(raw.toString('utf8')) : null } }];
  • Der HMAC läuft über raw, die Bytes, die die App signiert hat. Rechnest du ihn über das erneut serialisierte body, kommt eine andere Zeichenkette heraus, und die Prüfung schlägt fehl.
  • n8n gibt Header-Namen in Kleinbuchstaben aus, der Header heißt also x-signature.
  • Wer den Workflow öffnen kann, kann den Schlüssel im Code lesen. Die Payload-Referenz zeigt dieselbe Prüfung mit einem Node Crypto, bei dem der Schlüssel in einem n8n-Credential liegt.

Füge danach einen Node If mit einer Bedingung hinzu: Der boolesche Wert {{ $json.valid }} ist wahr.

Antworten, bevor der langsame Teil kommt

Lass jeden Zweig des If-Nodes in einem eigenen Node Respond to Webhook enden, mit Respond With auf No Data. Stell unter Options den Response Code im wahren Zweig auf 204 und im falschen auf 401. Was das iPhone mit jeder Antwort macht:

  • 204. Jede 2xx-Antwort gilt als zugestellt. Die Nodes hinter dem Node Respond to Webhook laufen trotzdem, mit demselben Item.
  • 401. Wird innerhalb der Synchronisierung nicht wiederholt. Der Payload bleibt in der Warteschlange des iPhones, die folgenden warten dahinter, und sie gehen raus, sobald die Schlüssel übereinstimmen: bei der nächsten Synchronisierung oder mit Jetzt erneut versuchen.
  • 500. Scheitert der Workflow, bevor ein Node Respond to Webhook läuft, antwortet n8n mit 500. Das iPhone versucht es insgesamt 3 Mal, im Abstand von 1 und dann 2 Sekunden, und behält den Payload dann für die nächste Synchronisierung.

Zwei Dinge sind anders als bei Android: Ein Payload, den dein Workflow mit 400, 413 oder 422 ablehnt, wird einmal am Tag erneut angeboten statt bei jeder Synchronisierung, und ein Payload, der älter als 7 Tage ist, wird bei der nächsten Zustellung verworfen, die n8n mit einem Fehler beantwortet.

Aus dem Payload Zeilen machen

Nach der 204 macht ein zweiter Code-Node aus dem Payload ein Item pro Datensatz. Es ist derselbe Code wie für Android:

const p = $input.first().json.payload;
if (!p || p.test) return [];

const rows = [];
for (const [type, value] of Object.entries(p)) {
  if (type === 'deleted_records' || !Array.isArray(value)) continue;
  for (const r of value) {
    if (!r || !r.uuid) continue; // daily totals and buckets carry no uuid
    rows.push({ json: {
      type,
      uuid: r.uuid,
      source: r.source ?? null,
      time: r.time ?? r.start_time ?? r.session_end_time ?? null,
      data: r,
    } });
  }
}
return rows;
  • Test senden und der Test-Ping der Einrichtung tragen "test": true und keine Datensätze, hinter diesem Node läuft dann also nichts.
  • Auf einem iPhone ist das source eines Datensatzes der Name, den Apple Health der App oder dem Gerät gibt, das ihn geschrieben hat, etwa Alex's Apple Watch, kein Paketname. Oft enthält er den Namen des Besitzers.
  • Die uuid einer Schlafnacht stammt von ihrer frühesten Phase. Sie bleibt also gleich, während die Nacht wächst, und der Upsert unten ersetzt die Nacht, wenn sie länger zurückkommt. Die Phasen einer Nacht tragen ihre eigene uuid und source in data.
  • Ein Lebensmittel ist ein Datensatz nutrition mit allen Nährstoffen darin und seinem name, wenn die App einen angegeben hat.
  • Reihen, die du unter Datenauflösung auf 1, 5 oder 15 Minuten oder stündlich stellst, kommen als Buckets ohne uuid an und werden hier übersprungen. Lass für diesen Workflow jeden Typ auf jedem Datensatz, das ist die Standardeinstellung.

In Postgres speichern, ohne Duplikate dank uuid

Derselbe Datensatz kann mehr als einmal ankommen: bei jedem Backfill, also beim Nachtragen des Verlaufs, und noch einmal aus der Warteschlange nach einer Sendung, die iOS abgebrochen hat. Nimm type und uuid als Schlüssel der Tabelle, beide als text:

CREATE TABLE health_records (
  type   text NOT NULL,
  uuid   text NOT NULL,
  source text,
  time   timestamptz,
  data   jsonb NOT NULL,
  PRIMARY KEY (type, uuid)
);

Füge einen Node Postgres mit der Operation Execute Query hinzu:

INSERT INTO health_records (type, uuid, source, time, data)
VALUES ($1, $2, $3, $4::timestamptz, $5::jsonb)
ON CONFLICT (type, uuid) DO UPDATE
SET source = EXCLUDED.source, time = EXCLUDED.time, data = EXCLUDED.data;

Füge unter Options die Query Parameters mit diesem Ausdruck hinzu:

{{ [ $json.type, $json.uuid, $json.source, $json.time, JSON.stringify($json.data) ] }}
  • Übergib Werte als Query Parameters, nie als {{ }} im SQL. n8n setzt einen Ausdruck im SQL als reinen Text ein. Ein Anführungszeichen in einem Wert, etwa das in Alex's Apple Watch, macht die Abfrage also kaputt.
  • Der Schlüssel ist type plus uuid, nicht uuid allein: Ein iPhone sendet einen Messwert der Aktivitätsenergie sowohl unter active_calories als auch unter total_calories.
  • Apple Health ändert einen Datensatz nicht an Ort und Stelle. Eine Änderung kommt als Löschung der alten uuid und als neuer Datensatz an; darum kümmert sich der nächste Schritt.

deleted_records anwenden

Ein Datensatz, der in Apple Health gelöscht wurde, wird in deleted_records eines späteren Payloads genannt, mit type und uuid. Ein dritter Code-Node, ebenfalls nach der 204:

const p = $input.first().json.payload;
return (p?.deleted_records ?? []).map(d => ({ json: { type: d.type, uuid: d.uuid } }));

Danach ein Postgres-Node mit Execute Query und den Query Parameters {{ [ $json.type, $json.uuid ] }}:

DELETE FROM health_records
WHERE type = $1 AND (uuid = $2 OR starts_with(uuid, $2 || '#'));

Die uuids eines iPhones enthalten nie ein #, für ein iPhone zählt also nur die erste Hälfte; die zweite ist für Messwerte von Herzfrequenz und Hauttemperatur von Android, damit ein Workflow beide bedienen kann. Eine gelöschte uuid, die du nicht hast, löscht nichts, und genau das verlangt die iOS-Payload-Seite.

Einen iPhone-Fall deckt die Abfrage oben nicht ab: Eine Schlaf-Löschung nennt eine Phase der Nacht, über ihre uuid in stages, nicht die Nacht. Um diese Phase aus der gespeicherten Nacht zu entfernen, fügst du einen zweiten Postgres-Node mit denselben Query Parameters hinzu:

UPDATE health_records
SET data = jsonb_set(data, '{stages}', (
  SELECT coalesce(jsonb_agg(s), '[]'::jsonb)
  FROM jsonb_array_elements(data->'stages') AS s
  WHERE s->>'uuid' IS DISTINCT FROM $2))
WHERE type = 'sleep' AND $1 = 'sleep'
  AND data->'stages' @> jsonb_build_array(jsonb_build_object('uuid', $2::text));

Das Feld duration_seconds der Nacht bleibt, wie es gesendet wurde. Für einen Typ, der in deletions_unavailable steht, kann bei dieser Synchronisierung nicht garantiert werden, dass alle Löschungen gemeldet sind: Starte einen Backfill aus der App, um ihn abzugleichen.

Willst du den Speicher nicht selbst bauen, entfernt der Empfänger des Life-Dashboard-Stacks Duplikate und Löschungen auf dieselbe Weise, mit Dashboards, einer API nur zum Lesen und einem MCP-Server obendrauf.

Stattdessen Google Sheets oder Telegram

Eine Zeile pro Tag in Google Sheets. Ein Code-Node nach der 204 nimmt die Tagessummen, die Apple Health so zählt wie die Health-App. Ein Spaziergang, den iPhone und Watch aufgezeichnet haben, zählt also einmal:

const p = $input.first().json.payload;
return (p?.daily_totals ?? []).map(d => ({ json: d }));

Danach ein Node Google Sheets mit Append or Update Row, einem Blatt mit den Spalten date, steps, distance_meters, active_calories und total_calories und date als Spalte für den Abgleich. Jeder Payload enthält heute und die zwei Tage davor, die Zeile von heute aktualisiert sich also mit jeder Synchronisierung. Auf einem iPhone kommt total_calories nur an Tagen mit Ruheenergie, die ein iPhone ohne Apple Watch meist nicht aufzeichnet.

Eine Telegram-Nachricht pro neuem Gewicht. Hinter dem Node für die Datensätze behält ein Node Filter die Items, bei denen {{ $json.type }} gleich weight ist. Ein Node Remove Duplicates mit Remove Items Processed in Previous Executions, Keep Items Where auf Value Is New und {{ $json.uuid }} als Wert für den Abgleich verhindert eine zweite Nachricht, wenn dieselbe Wägung bei einem Backfill noch einmal kommt. Danach ein Node Telegram mit Send Message und dem Text Weight: {{ $json.data.kilograms }} kg.

Ein iPhone und ein Android-Telefon in einem Workflow

  • Das source auf oberster Ebene ist healthkit_ios von einem iPhone und health_connect von Android.
  • Die Herzfrequenzvariabilität ist SDNN von einem iPhone und RMSSD von Android, unter demselben Schlüssel. Speichere das source der obersten Ebene mit jedem Datensatz, damit die beiden getrennt bleiben.
  • Der type eines Trainings ist von einem iPhone ein Name wie running und von Android die Nummer von Health Connect als Zeichenkette, etwa "56".
  • Schlafphasen von einem iPhone enthalten in_bed, die Zeit im Bett rund um die Phasen.
  • Die Bildschirmzeit kommt nur von Android, als eigener Payload.

Die Schritte für Datensätze, Upsert und Löschungen auf dieser Seite stammen aus dem Workflow in Health Connect mit n8n. Die Code-Nodes und das SQL wurden hier gegen einen iPhone-Payload in Node.js und Postgres geprüft, nicht in einem laufenden n8n, an das ein iPhone sendet. Probier es also mit Test senden und Jetzt synchronisieren aus, bevor du dich darauf verlässt.

Grenzen

  • n8n kann das iPhone nicht nach einem Zeitraum fragen. Starte einen Backfill auf dem iPhone, von 30 Tagen bis Alles, mit Verlauf senden unter Was senden.
  • iOS entscheidet, wann die App im Hintergrund läuft, Synchronisierungen können also später kommen, als der Zeitplan sagt. Für eine genaue Zeit führt eine Automation in Kurzbefehle Gesundheitsdaten synchronisieren aus.
  • Weil die 204 zuerst rausgeht, können zwei Payloads gleichzeitig gespeichert werden. Payloads tragen eine sequence, die nur steigt; nutze sie, wenn die Reihenfolge zählt, etwa bei daily_totals.

FAQ

Unterscheidet sich der Workflow von dem für Android?

Nur in den Details auf dieser Seite. Der Webhook-Node, die Signaturprüfung, die Antworten und der Upsert sind dieselben, ein Workflow kann also beide Telefone annehmen. Der zusätzliche Schritt ist die Löschung einer Schlafphase, die nur ein iPhone sendet.

Funktioniert das in der n8n Cloud?

Ja. Die Production-URL eines veröffentlichten Workflows ist öffentliches HTTPS, und die n8n Cloud stellt dem Code-Node das Modul crypto bereit. Selbst gehostetes n8n braucht für denselben Code NODE_FUNCTION_ALLOW_BUILTIN=crypto.

Warum schlägt die Signaturprüfung bei jeder Anfrage fehl?

Meist liegt es an einem von drei Dingen: Raw Body ist aus, es gibt also kein binäres data zum Hashen; der HMAC läuft über das geparste body statt über die rohen Bytes; oder der Schlüssel in n8n weicht von dem in der App ab. Kopiere den Schlüssel noch einmal und verwende ihn als reinen Text.

Erreichen Daten der Apple Watch n8n?

Ja. Die Uhr schreibt in Apple Health auf dem iPhone, und die App sendet die Daten weiter, sobald die Uhr mit dem iPhone synchronisiert hat. Apple Watch in Home Assistant listet auf, was eine Uhr üblicherweise aufzeichnet.

Kann ich einen Payload sehen, bevor ich den Workflow baue?

Ja. Payload-Vorschau unter Was senden in der App zeigt die letzten 7 Tage als Payload. In n8n zeigt die Test-URL mit Listen for Test Event eine echte Anfrage im Editor.
