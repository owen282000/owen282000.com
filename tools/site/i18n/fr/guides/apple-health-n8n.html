Comment envoyer les données d’Apple Health vers n8n ?

Installez Life Dashboard Companion sur votre iPhone et saisissez-y comme webhook l’URL de production d’un nœud Webhook n8n. Dans n8n, activez l’option Raw Body du nœud Webhook, vérifiez le HMAC de l’en-tête X-Signature dans un nœud Code, répondez 204 avec un nœud Respond to Webhook, puis stockez chaque enregistrement avec son type et son uuid comme clé. Tout ce que contient Apple Health (l’app Santé de l’iPhone) arrive ainsi dans n8n, que cela vienne de l’iPhone, d’une Apple Watch ou d’une autre application qui y écrit.

L’application iPhone envoie le payload de l’application Android : le workflow est donc celui de Santé Connect vers n8n, et un seul workflow accepte les deux téléphones. Cette page reprend le workflow complet, avec les endroits où un payload d’iPhone diffère. Le payload lui-même, les nouvelles tentatives et la file sont décrits dans Apple Santé vers un webhook.

Ce qu’il vous faut

  • Life Dashboard Companion pour iPhone sur iOS 17 ou plus récent. {{status:ios}}
  • n8n, sur n8n Cloud ou auto-hébergé, joignable depuis l’iPhone. Utilisez HTTPS. iOS n’autorise le simple http:// que vers une adresse IP, un nom en .local ou un nom sans point, et demande une fois l’accès au réseau local : autorisez-le pour un n8n installé chez vous.
  • De la place pour les grosses requêtes. n8n accepte jusqu’à 16 Mo par défaut, mais un reverse proxy placé devant doit l’autoriser aussi : nginx autorise 1 Mo par défaut.
  • Le module crypto dans le nœud Code. n8n Cloud le fournit. Sur un n8n auto-hébergé, définissez NODE_FUNCTION_ALLOW_BUILTIN=crypto, sur le task runner si vous en utilisez un.

Le workflow en un coup d’œil

Webhook (POST, Raw Body)
  -> Code: check signature
  -> If: valid is true
       true  -> Respond to Webhook (204)
                  -> Code: records    -> Postgres: upsert
                  -> Code: deletions  -> Postgres: delete
       false -> Respond to Webhook (401)

La réponse part avant le travail en base de données : l’application abandonne une tentative dès que la connexion reste immobile 10 secondes.

Configurer le nœud Webhook

  1. Ajoutez un nœud Webhook. Réglez HTTP Method sur POST et choisissez un Path, par exemple life-dashboard.
  2. Réglez Respond sur Using 'Respond to Webhook' Node. Avec Immediately, n8n répond 200 avant que la vérification de la signature ne s’exécute : un payload dont la signature est mauvaise compte alors quand même comme livré.
  3. Sous Options, ajoutez Raw Body et activez-le. Le nœud fournit alors les octets tels qu’ils sont arrivés dans la propriété binaire data, à côté du JSON analysé dans body et des en-têtes dans headers.
  4. Publiez le workflow et copiez l’URL de production. L’URL de test n’écoute que pendant que l’éditeur attend un événement de test. Une synchronisation envoyée alors que rien n’écoute reçoit un 404, et l’iPhone garde ce payload et les suivants dans sa file jusqu’à ce que l’URL réponde de nouveau.

Dans l’application, touchez Ajouter une destination dans l’onglet Santé, saisissez l’URL de production et touchez Ajouter un webhook. Sur la fiche qui s’ouvre, touchez Générer sous Secret de signature HMAC, touchez Copier le secret pour l’étape suivante, puis Enregistrer.

Vérifier la signature dans un nœud Code

L’iPhone signe exactement comme l’application Android : X-Signature: sha256=<hex>, le HMAC-SHA256 du corps brut avec votre secret comme clé. Ajoutez un nœud Code en JavaScript, en mode Run Once for All Items :

const crypto = require('crypto');

// The secret as the app shows it. Use it as text: don't hex-decode it.
const SECRET = 'paste-the-secret-from-the-app';

const item = $input.first();
const raw = await this.helpers.getBinaryDataBuffer(0, 'data');
const expected = Buffer.from(
  'sha256=' + crypto.createHmac('sha256', SECRET).update(raw).digest('hex')
);
const presented = Buffer.from(item.json.headers['x-signature'] || '');
const valid = presented.length === expected.length &&
  crypto.timingSafeEqual(presented, expected);

return [{ json: { valid, payload: valid ? JSON.parse(raw.toString('utf8')) : null } }];
  • Le HMAC est calculé sur raw, les octets que l’application a signés. Le calculer sur body sérialisé de nouveau donne une chaîne différente, et la vérification échoue.
  • n8n fournit les noms d’en-têtes en minuscules : l’en-tête est donc x-signature.
  • Quiconque peut ouvrir le workflow peut lire le secret dans le code. La référence du payload montre la même vérification avec un nœud Crypto, qui garde le secret dans un identifiant n8n.

Ajoutez ensuite un nœud If avec une seule condition : le booléen {{ $json.valid }} est vrai.

Répondre avant la partie lente

Terminez chaque branche du nœud If par son propre nœud Respond to Webhook, avec Respond With réglé sur No Data. Sous Options, réglez Response Code sur 204 pour la branche vraie et sur 401 pour la branche fausse. Voici ce que l’iPhone fait de chaque réponse :

  • 204. Toute réponse 2xx compte comme une livraison. Les nœuds placés après le nœud Respond to Webhook s’exécutent quand même, avec le même élément.
  • 401. Pas de nouvelle tentative pendant la synchronisation. Le payload reste dans la file de l’iPhone, les suivants attendent derrière lui, et ils partent une fois que les secrets concordent : à la synchronisation suivante, ou avec Réessayer maintenant.
  • 500. Si le workflow échoue avant qu’un nœud Respond to Webhook ne s’exécute, n8n répond 500. L’iPhone essaie 3 fois en tout, à 1 puis 2 secondes d’écart, puis garde le payload pour la synchronisation suivante.

Deux points diffèrent d’Android : un payload que votre workflow refuse avec un 400, un 413 ou un 422 est proposé de nouveau une fois par jour plutôt qu’à chaque synchronisation, et un payload de plus de 7 jours est abandonné à la livraison suivante à laquelle n8n répond par une erreur.

Transformer le payload en lignes

Après le 204, un deuxième nœud Code transforme le payload en un élément par enregistrement. C’est le même code que pour Android :

const p = $input.first().json.payload;
if (!p || p.test) return [];

const rows = [];
for (const [type, value] of Object.entries(p)) {
  if (type === 'deleted_records' || !Array.isArray(value)) continue;
  for (const r of value) {
    if (!r || !r.uuid) continue; // daily totals and buckets carry no uuid
    rows.push({ json: {
      type,
      uuid: r.uuid,
      source: r.source ?? null,
      time: r.time ?? r.start_time ?? r.session_end_time ?? null,
      data: r,
    } });
  }
}
return rows;
  • Envoyer un test et le Ping de test de la configuration portent "test": true et aucun enregistrement : rien ne s’exécute donc après ce nœud.
  • Sur un iPhone, le champ source d’un enregistrement est le nom qu’Apple Santé donne à l’application ou à l’appareil qui l’a écrit, par exemple Alex's Apple Watch, pas un nom de paquet. Il contient souvent le nom du propriétaire.
  • L’uuid d’une nuit de sommeil vient de sa première phase : il reste donc le même pendant que la nuit s’allonge, et l’upsert ci-dessous remplace la nuit quand elle revient plus longue. Les phases d’une nuit portent leur propre uuid et leur propre source dans data.
  • Un aliment forme un seul enregistrement nutrition avec tous ses nutriments, et son name quand l’application en a donné un.
  • Les séries que vous réglez sur 1, 5 ou 15 minutes ou sur une heure sous Résolution des données arrivent sous forme de fenêtres agrégées sans uuid et sont ignorées ici. Laissez chaque type sur chaque enregistrement pour ce workflow : c’est le réglage par défaut.

Stocker dans Postgres, en dédoublonnant sur uuid

Le même enregistrement peut arriver plusieurs fois : à chaque backfill (le rattrapage de l’historique), et de nouveau depuis la file après un envoi interrompu par iOS. Donnez à la table la clé type et uuid, tous deux en text :

CREATE TABLE health_records (
  type   text NOT NULL,
  uuid   text NOT NULL,
  source text,
  time   timestamptz,
  data   jsonb NOT NULL,
  PRIMARY KEY (type, uuid)
);

Ajoutez un nœud Postgres avec l’opération Execute Query :

INSERT INTO health_records (type, uuid, source, time, data)
VALUES ($1, $2, $3, $4::timestamptz, $5::jsonb)
ON CONFLICT (type, uuid) DO UPDATE
SET source = EXCLUDED.source, time = EXCLUDED.time, data = EXCLUDED.data;

Sous Options, ajoutez Query Parameters avec cette expression :

{{ [ $json.type, $json.uuid, $json.source, $json.time, JSON.stringify($json.data) ] }}
  • Passez les valeurs en Query Parameters, jamais sous forme de {{ }} dans le SQL. n8n colle une expression dans le SQL comme du texte brut : une apostrophe dans une valeur, comme celle de Alex's Apple Watch, casse donc la requête.
  • La clé est type plus uuid, pas uuid seul : un iPhone envoie un même échantillon d’énergie active sous active_calories et sous total_calories.
  • Apple Santé ne modifie pas un enregistrement sur place. Une modification arrive sous la forme d’une suppression de l’ancien uuid et d’un nouvel enregistrement, ce que traite l’étape suivante.

Appliquer deleted_records

Un enregistrement supprimé dans Apple Santé est nommé dans le champ deleted_records d’un payload ultérieur, avec son type et son uuid. Un troisième nœud Code, lui aussi après le 204 :

const p = $input.first().json.payload;
return (p?.deleted_records ?? []).map(d => ({ json: { type: d.type, uuid: d.uuid } }));

Puis un nœud Postgres avec Execute Query et les Query Parameters {{ [ $json.type, $json.uuid ] }} :

DELETE FROM health_records
WHERE type = $1 AND (uuid = $2 OR starts_with(uuid, $2 || '#'));

Les uuid d’un iPhone ne contiennent jamais de # : pour un iPhone, seule la première moitié compte donc ; la seconde sert aux échantillons de fréquence cardiaque et de température cutanée d’Android, et permet à un même workflow de servir les deux. Un uuid supprimé que vous n’avez pas ne supprime rien, ce que demande justement la page du payload iOS.

Un cas propre à l’iPhone que la requête ci-dessus ne couvre pas : la suppression d’un sommeil nomme une phase de la nuit, par son uuid dans stages, pas la nuit. Pour retirer cette phase de la nuit stockée, ajoutez un second nœud Postgres avec les mêmes Query Parameters :

UPDATE health_records
SET data = jsonb_set(data, '{stages}', (
  SELECT coalesce(jsonb_agg(s), '[]'::jsonb)
  FROM jsonb_array_elements(data->'stages') AS s
  WHERE s->>'uuid' IS DISTINCT FROM $2))
WHERE type = 'sleep' AND $1 = 'sleep'
  AND data->'stages' @> jsonb_build_array(jsonb_build_object('uuid', $2::text));

Le champ duration_seconds de la nuit reste tel qu’il a été envoyé. Un type listé dans deletions_unavailable ne peut pas être garanti pour cette synchronisation : lancez un backfill depuis l’application pour le réconcilier.

Si vous préférez ne pas construire le stockage vous-même, le récepteur de la stack Life Dashboard dédoublonne et supprime de la même façon, avec en plus des tableaux de bord, une API en lecture seule et un serveur MCP.

Google Sheets ou Telegram à la place

Une ligne par jour dans Google Sheets. Un nœud Code placé après le 204 prend les totaux quotidiens, qu’Apple Santé compte comme le fait l’app Santé : une marche enregistrée par l’iPhone et la montre n’est donc comptée qu’une fois :

const p = $input.first().json.payload;
return (p?.daily_totals ?? []).map(d => ({ json: d }));

Puis un nœud Google Sheets avec Append or Update Row, une feuille avec les colonnes date, steps, distance_meters, active_calories et total_calories, et date comme colonne de correspondance. Chaque payload contient aujourd’hui et les deux jours précédents : la ligne du jour se met donc à jour à chaque synchronisation. Sur un iPhone, total_calories ne vient que les jours où il y a de l’énergie au repos, ce qu’un iPhone sans Apple Watch n’enregistre généralement pas.

Un message Telegram à chaque nouveau poids. Après le nœud des enregistrements, un nœud Filter garde les éléments dont {{ $json.type }} vaut weight. Un nœud Remove Duplicates avec Remove Items Processed in Previous Executions, Keep Items Where réglé sur Value Is New et {{ $json.uuid }} comme valeur de dédoublonnage empêche un second message quand la même pesée revient dans un backfill. Puis un nœud Telegram avec Send Message et le texte Weight: {{ $json.data.kilograms }} kg.

Un iPhone et un téléphone Android dans un seul workflow

  • Le champ source de premier niveau vaut healthkit_ios depuis un iPhone et health_connect depuis Android.
  • La variabilité de la fréquence cardiaque est le SDNN depuis un iPhone et le RMSSD depuis Android, sous la même clé. Stockez le champ source de premier niveau avec chaque enregistrement pour que les deux restent séparés.
  • Le type d’un entraînement est un nom comme running depuis un iPhone, et le numéro de Santé Connect sous forme de chaîne, comme "56", depuis Android.
  • Les phases de sommeil d’un iPhone comprennent in_bed, le temps passé au lit autour des phases.
  • Le temps d’écran ne vient que d’Android, dans son propre payload.

Les étapes des enregistrements, de l’upsert et de la suppression de cette page viennent du workflow de Santé Connect vers n8n. Les nœuds Code et le SQL ont été vérifiés ici avec un payload d’iPhone dans Node.js et Postgres, pas dans un n8n en fonctionnement recevant les envois d’un iPhone : essayez donc avec Envoyer un test et Synchroniser maintenant avant de vous y fier.

Les limites

  • n8n ne peut pas demander une plage de dates à l’iPhone. Lancez un backfill sur l’iPhone, de 30 jours à Tout l’historique, avec Envoyer l’historique sous Données à envoyer.
  • iOS décide du moment où l’application s’exécute en arrière-plan : les synchronisations peuvent donc arriver plus tard que prévu. Pour une heure précise, une automatisation Raccourcis lance Synchroniser les données de santé.
  • Comme le 204 part en premier, deux payloads peuvent être stockés en même temps. Les payloads portent une sequence qui ne fait qu’augmenter ; utilisez-la quand l’ordre compte, par exemple pour daily_totals.

FAQ

Le workflow est-il différent de celui d’Android ?

Seulement dans les détails décrits sur cette page. Le nœud Webhook, la vérification de la signature, les réponses et l’upsert sont les mêmes : un seul workflow peut donc accepter les deux téléphones. L’étape supplémentaire est la suppression d’une phase de sommeil, que seul un iPhone envoie.

Est-ce que cela fonctionne sur n8n Cloud ?

Oui. L’URL de production d’un workflow publié est en HTTPS public, et n8n Cloud fournit le module crypto au nœud Code. Un n8n auto-hébergé a besoin de NODE_FUNCTION_ALLOW_BUILTIN=crypto pour le même code.

Pourquoi la vérification de la signature échoue-t-elle à chaque requête ?

En général pour l’une de ces trois raisons : Raw Body est désactivé, et il n’y a donc pas de data binaire à hacher ; le HMAC est calculé sur le body analysé au lieu des octets bruts ; ou le secret dans n8n diffère de celui de l’application. Copiez de nouveau le secret et utilisez-le comme du texte brut.

Les données de l’Apple Watch arrivent-elles dans n8n ?

Oui. La montre écrit dans Apple Santé sur l’iPhone, et l’application les transmet une fois que la montre s’est synchronisée avec l’iPhone. Le guide L’Apple Watch dans Home Assistant énumère ce qu’une montre enregistre habituellement.

Puis-je voir un payload avant de construire le workflow ?

Oui. Aperçu du payload, sous Données à envoyer dans l’application, montre les 7 derniers jours sous forme de payload. Dans n8n, l’URL de test avec Listen for Test Event affiche une vraie requête dans l’éditeur.
