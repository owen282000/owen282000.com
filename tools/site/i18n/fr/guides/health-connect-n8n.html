Comment envoyer les données de Health Connect vers n8n ?

Installez Life Dashboard Companion, une application Android open source, et saisissez-y comme webhook l’URL de production d’un nœud Webhook n8n. Dans n8n, activez l’option Raw Body du nœud Webhook, vérifiez le HMAC de l’en-tête X-Signature dans un nœud Code, répondez 204 avec un nœud Respond to Webhook, puis stockez chaque enregistrement avec son type et son uuid comme clé. Les données de Samsung Health, Garmin Connect, Google Health, Oura et Withings arrivent ainsi dans n8n, car ces applications les écrivent dans Health Connect (Santé Connect en français) sur le téléphone.

L’application iPhone envoie les données d’Apple Santé dans le même format : un seul workflow accepte donc les deux téléphones. Cette page traite du côté n8n. Le payload lui-même, les nouvelles tentatives et la file d’attente sont décrits dans Santé Connect vers un webhook.

Ce qu’il vous faut

  • Life Dashboard Companion pour Android sur Android 9 ou plus récent avec Santé Connect. {{status:android}}
  • Ou l’application iPhone sur iOS 17 ou plus récent. {{status:ios}}
  • n8n, sur n8n Cloud ou auto-hébergé, joignable depuis le téléphone. Utilisez HTTPS. Le HTTP non chiffré sur votre propre réseau demande d’activer Autoriser les webhooks en HTTP non chiffré sous Plus > Avancé dans l’application Android ; l’application iPhone n’autorise le HTTP non chiffré que vers une adresse IP, un nom en .local ou un nom sans point.
  • De la place pour les grosses requêtes. Autorisez au moins 10 Mo par requête. n8n accepte jusqu’à 16 Mo par défaut, mais un reverse proxy placé devant doit l’autoriser aussi : nginx autorise 1 Mo par défaut.
  • Le module crypto dans le nœud Code. n8n Cloud le fournit. Sur un n8n auto-hébergé, définissez NODE_FUNCTION_ALLOW_BUILTIN=crypto, sur le task runner si vous en utilisez un.

Le workflow en un coup d’œil

Webhook (POST, Raw Body)
  -> Code: check signature
  -> If: valid is true
       true  -> Respond to Webhook (204)
                  -> Code: records    -> Postgres: upsert
                  -> Code: deletions  -> Postgres: delete
       false -> Respond to Webhook (401)

La réponse part avant le travail en base de données, car l’application attend une réponse au plus 10 secondes.

Configurer le nœud Webhook

  1. Ajoutez un nœud Webhook. Réglez HTTP Method sur POST et choisissez un Path, par exemple life-dashboard.
  2. Réglez Respond sur Using 'Respond to Webhook' Node. Avec Immediately, n8n répond 200 avant que la vérification de la signature ne s’exécute : un payload dont la signature est mauvaise compte alors quand même comme livré.
  3. Sous Options, ajoutez Raw Body et activez-le. Le nœud fournit alors les octets tels qu’ils sont arrivés dans la propriété binaire data, à côté du JSON analysé dans body et des en-têtes dans headers.
  4. Publiez le workflow et copiez l’URL de production. L’URL de test n’écoute que pendant que l’éditeur attend un événement de test, et l’URL de production ne fonctionne que tant que le workflow est publié. Une synchronisation envoyée à un autre moment reçoit un 404, et l’application garde ce payload et les suivants jusqu’à ce que l’URL réponde de nouveau.

Dans l’application, touchez Ajouter une destination (ou Utiliser votre propre serveur si rien n’est encore configuré) dans l’onglet Santé, collez l’URL de production sous URL de webhook et touchez Ajouter un webhook. Sur la page qui s’ouvre, touchez Générer sous Secret de signature HMAC (facultatif), copiez le secret avec Copier le secret pour l’étape suivante et touchez Enregistrer.

Vérifier la signature dans un nœud Code

Chaque requête porte X-Signature: sha256=<hex>, le HMAC-SHA256 du corps brut avec votre secret comme clé. Ajoutez un nœud Code en JavaScript, en mode Run Once for All Items :

const crypto = require('crypto');

// The secret as the app shows it. Use it as text: don't hex-decode it.
const SECRET = 'paste-the-secret-from-the-app';

const item = $input.first();
const raw = await this.helpers.getBinaryDataBuffer(0, 'data');
const expected = Buffer.from(
  'sha256=' + crypto.createHmac('sha256', SECRET).update(raw).digest('hex')
);
const presented = Buffer.from(item.json.headers['x-signature'] || '');
const valid = presented.length === expected.length &&
  crypto.timingSafeEqual(presented, expected);

return [{ json: { valid, payload: valid ? JSON.parse(raw.toString('utf8')) : null } }];
  • Le HMAC est calculé sur raw, les octets que l’application a signés. Le calculer sur body sérialisé de nouveau donne une chaîne différente, et la vérification échoue.
  • n8n fournit les noms d’en-têtes en minuscules : l’en-tête est donc x-signature.
  • timingSafeEqual compare en temps constant et lève une exception si les entrées n’ont pas la même longueur : la vérification de la longueur vient donc en premier.
  • Quiconque peut ouvrir le workflow peut lire le secret dans le code. Si cela compte pour vous, la référence du payload montre la même vérification avec un nœud Crypto, qui garde le secret dans un identifiant n8n.

Ajoutez ensuite un nœud If avec une seule condition : le booléen {{ $json.valid }} est vrai.

Répondre avant la partie lente

Terminez chaque branche du nœud If par son propre nœud Respond to Webhook, avec Respond With réglé sur No Data. Sous Options, réglez Response Code sur 204 pour la branche vraie et sur 401 pour la branche fausse.

  • 204. L’application compte toute réponse 2xx comme une livraison. Les nœuds placés après le nœud Respond to Webhook s’exécutent quand même, avec le même élément.
  • 401. L’application ne retente pas. Elle garde le payload, et les suivants, dans sa file d’attente et les livre une fois que les secrets concordent.
  • 500. Si le workflow échoue avant qu’un nœud Respond to Webhook ne s’exécute, n8n répond 500. L’application essaie 3 fois en tout, puis garde le payload pour la synchronisation suivante.

Transformer le payload en lignes

Après le 204, un deuxième nœud Code transforme le payload en un élément par enregistrement :

const p = $input.first().json.payload;
if (!p || p.test) return [];

const rows = [];
for (const [type, value] of Object.entries(p)) {
  if (type === 'deleted_records' || !Array.isArray(value)) continue;
  for (const r of value) {
    if (!r || !r.uuid) continue; // daily totals and buckets carry no uuid
    rows.push({ json: {
      type,
      uuid: r.uuid,
      source: r.source ?? null,
      time: r.time ?? r.start_time ?? r.session_end_time ?? null,
      data: r,
    } });
  }
}
return rows;

Un Envoyer un test depuis l’application ne donne aucune ligne : rien ne s’exécute donc après ce nœud. Les séries que vous réglez sur 1, 5 ou 15 minutes ou sur une heure sous Résolution des données arrivent sous forme de fenêtres agrégées sans uuid et sont ignorées ici : laissez la résolution des données sur chaque enregistrement pour ce workflow, ou stockez ces fenêtres dans leur propre table, avec la série et bucket_start comme clé.

Stocker dans Postgres, en dédoublonnant sur uuid

Le même enregistrement peut arriver plusieurs fois : après une nouvelle tentative, quand sa source le modifie, et à chaque backfill (le rattrapage de l’historique). Donnez à la table la clé type et uuid, tous deux en text :

CREATE TABLE health_records (
  type   text NOT NULL,
  uuid   text NOT NULL,
  source text,
  time   timestamptz,
  data   jsonb NOT NULL,
  PRIMARY KEY (type, uuid)
);

Ajoutez un nœud Postgres avec l’opération Execute Query :

INSERT INTO health_records (type, uuid, source, time, data)
VALUES ($1, $2, $3, $4::timestamptz, $5::jsonb)
ON CONFLICT (type, uuid) DO UPDATE
SET source = EXCLUDED.source, time = EXCLUDED.time, data = EXCLUDED.data;

Sous Options, ajoutez Query Parameters avec cette expression :

{{ [ $json.type, $json.uuid, $json.source, $json.time, JSON.stringify($json.data) ] }}
  • Passez les valeurs en Query Parameters, jamais sous forme de {{ }} dans le SQL. n8n colle une expression dans le SQL comme du texte brut : une apostrophe dans une valeur casse donc la requête.
  • La clé est type plus uuid, pas uuid seul. Les échantillons de fréquence cardiaque et de température cutanée ont un uuid de la forme <record id>#<epoch ms>, et un iPhone envoie un même échantillon d’énergie active sous active_calories et sous total_calories.
  • Depuis Android, un enregistrement modifié arrive avec le même uuid et de nouvelles valeurs, et l’upsert remplace l’ancienne ligne. Apple Santé ne modifie pas sur place : une modification arrive sous la forme d’une suppression et d’un nouvel enregistrement.

Appliquer deleted_records

Un enregistrement supprimé dans Santé Connect ou Apple Santé est nommé dans le champ deleted_records d’un payload ultérieur, avec son type et son uuid. Un troisième nœud Code, lui aussi après le 204 :

const p = $input.first().json.payload;
return (p?.deleted_records ?? []).map(d => ({ json: { type: d.type, uuid: d.uuid } }));

Puis un nœud Postgres avec Execute Query et les Query Parameters {{ [ $json.type, $json.uuid ] }} :

DELETE FROM health_records
WHERE type = $1 AND (uuid = $2 OR starts_with(uuid, $2 || '#'));

La seconde moitié supprime les échantillons d’un enregistrement de fréquence cardiaque ou de température cutanée venu d’Android. Depuis un iPhone, la suppression d’un sommeil nomme une phase de la nuit, pas la nuit : cette requête laisse donc la nuit en place. Un type listé dans deletions_unavailable ne peut pas être garanti pour cette synchronisation : lancez un backfill depuis l’application pour le réconcilier.

Une fois les enregistrements dans Postgres, un modèle peut les lire avec un rôle en lecture seule et un serveur MCP : le guide Les données de Santé Connect via MCP décrit cette voie. Si vous préférez ne pas construire le stockage vous-même, le récepteur de la stack Life Dashboard dédoublonne et supprime de la même façon, avec en plus des tableaux de bord, une API en lecture seule et un serveur MCP.

Google Sheets ou Telegram à la place

Une ligne par jour dans Google Sheets. Un nœud Code placé après le 204 prend les totaux quotidiens, qui ne comptent une marche qu’une fois même quand le téléphone et la montre l’ont tous deux enregistrée :

const p = $input.first().json.payload;
return (p?.daily_totals ?? []).map(d => ({ json: d }));

Puis un nœud Google Sheets avec Append or Update Row, une feuille avec les colonnes date, steps, distance_meters, active_calories et total_calories, et date comme colonne de correspondance. La ligne du jour est un total en cours et se met à jour à chaque synchronisation. Un champ manque les jours sans données pour ce type.

Un message Telegram à chaque nouveau poids. Après le nœud des enregistrements, un nœud Filter garde les éléments dont {{ $json.type }} vaut weight. Un nœud Remove Duplicates avec Remove Items Processed in Previous Executions, Keep Items Where réglé sur Value Is New et {{ $json.uuid }} comme valeur de dédoublonnage empêche un second message quand la même pesée revient dans un backfill. Puis un nœud Telegram avec Send Message et le texte Weight: {{ $json.data.kilograms }} kg.

Samsung Health, Garmin et Apple Santé dans un seul workflow

  • Le champ source de chaque enregistrement est le nom de paquet de l’application qui l’a écrit, par exemple com.sec.android.app.shealth pour Samsung Health, com.garmin.android.apps.connectmobile pour Garmin Connect ou com.fitbit.FitbitMobile pour Google Health. Filtrez dessus pour router une marque.
  • Le champ source de premier niveau vaut health_connect depuis Android et healthkit_ios depuis un iPhone. Sur un iPhone, le champ source d’un enregistrement est le nom qu’Apple Santé donne à l’application ou à l’appareil.
  • La variabilité de la fréquence cardiaque est le RMSSD depuis Android et le SDNN depuis un iPhone, sous la même clé. Si les deux téléphones envoient vers ce workflow, stockez le champ source de premier niveau avec chaque enregistrement pour que les deux restent séparés.
  • Les types que chaque application écrit, et ceux qu’elle garde pour elle, sont décrits dans Les types de données de Santé Connect, application par application.

Les limites

  • n8n ne peut pas demander une plage de dates au téléphone. Lancez un backfill sur le téléphone, de 30 jours à Tout l’historique, avec Envoyer l’historique, dans Données à envoyer de l’onglet Santé.
  • Comme le 204 part en premier, deux payloads peuvent être stockés en même temps. Les payloads portent aussi une sequence qui ne fait qu’augmenter : le guide Santé Connect vers un webhook explique comment l’utiliser quand l’ordre compte, par exemple pour daily_totals.
  • Le temps d’écran arrive dans son propre payload, avec "source": "screen_time", depuis les URL de l’onglet Temps d’écran. Il n’a pas de uuid d’enregistrement : le nœud des enregistrements ci-dessus l’ignore donc.

FAQ

Est-ce que cela fonctionne sur n8n Cloud ?

Oui. L’URL de production d’un workflow publié est en HTTPS public, et n8n Cloud fournit le module crypto au nœud Code. Un n8n auto-hébergé a besoin de NODE_FUNCTION_ALLOW_BUILTIN=crypto pour le même code.

Pourquoi la vérification de la signature échoue-t-elle à chaque requête ?

En général pour l’une de ces trois raisons : Raw Body est désactivé, et il n’y a donc pas de data binaire à hacher ; le HMAC est calculé sur le body analysé au lieu des octets bruts ; ou le secret dans n8n diffère de celui de l’application. Copiez de nouveau le secret et utilisez-le comme du texte brut.

Puis-je me passer de la signature ?

Oui. Sans secret, l’application n’envoie pas de X-Signature. Protégez l’URL autrement, par exemple avec Header Auth sur le nœud Webhook et le même en-tête sous En-têtes sur la page de l’adresse dans l’application.

Les données de Samsung Health arrivent-elles dans n8n ?

Oui, dès que Samsung Health les partage avec Santé Connect : pas, exercice, sommeil avec ses phases, fréquence cardiaque, tension artérielle, poids et d’autres encore. Samsung Health ne partage ni la variabilité de la fréquence cardiaque ni la fréquence cardiaque au repos avec Santé Connect : ces données n’arrivent donc pas.

Puis-je voir un payload avant de construire le workflow ?

Oui. Aperçu du payload, sous Données à envoyer dans l’onglet Santé de l’application, montre ce que la prochaine synchronisation enverrait. Dans n8n, l’URL de test avec Listen for Test Event affiche une vraie requête dans l’éditeur.
