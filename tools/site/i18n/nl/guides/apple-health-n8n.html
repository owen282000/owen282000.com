Hoe krijg ik Apple Health-data in n8n?

Installeer Life Dashboard Companion op je iPhone en vul de productie-URL van een Webhook-node in n8n in als webhook. Zet in n8n de optie Raw Body van de Webhook-node aan, controleer de HMAC uit X-Signature in een Code-node, antwoord met 204 via een Respond to Webhook-node en sla daarna elk record op met type en uuid als sleutel. Zo komt alles uit Apple Health (de app Gezondheid op je iPhone) in n8n terecht: van de iPhone, van een Apple Watch of van een andere app die daar schrijft.

De iPhone-app stuurt de payload van de Android-app, dus de workflow is die uit Health Connect naar n8n, en één workflow werkt voor beide telefoons. Op deze pagina staat de hele workflow nog een keer, met de plekken waar een iPhone-payload afwijkt. De payload zelf, nieuwe pogingen en de wachtrij staan in Apple Health naar een webhook.

Wat je nodig hebt

  • Life Dashboard Companion voor iPhone op iOS 17 of nieuwer. {{status:ios}}
  • n8n, op n8n Cloud of zelf gehost, bereikbaar vanaf de iPhone. Gebruik HTTPS. iOS staat onversleuteld http:// alleen toe naar een IP-adres, een .local-naam of een naam zonder punt, en vraagt één keer om toegang tot het lokale netwerk: sta dat toe voor een n8n bij je thuis.
  • Ruimte voor grote verzoeken. n8n accepteert standaard tot 16 MB, maar een reverse proxy ervoor moet dat ook toestaan: nginx staat standaard 1 MB toe.
  • De module crypto in de Code-node. n8n Cloud levert die mee. Op zelf gehoste n8n stel je NODE_FUNCTION_ALLOW_BUILTIN=crypto in, op de task runner als je die gebruikt.

De workflow in één oogopslag

Webhook (POST, Raw Body)
  -> Code: check signature
  -> If: valid is true
       true  -> Respond to Webhook (204)
                  -> Code: records    -> Postgres: upsert
                  -> Code: deletions  -> Postgres: delete
       false -> Respond to Webhook (401)

Het antwoord gaat de deur uit vóór het databasewerk: de app geeft een poging op zodra de verbinding 10 seconden stilstaat.

De Webhook-node instellen

  1. Voeg een Webhook-node toe. Zet HTTP Method op POST en kies een Path, zoals life-dashboard.
  2. Zet Respond op Using 'Respond to Webhook' Node. Met Immediately antwoordt n8n met 200 voordat de handtekeningcontrole draait, dus een payload met een foute handtekening telt dan toch als afgeleverd.
  3. Voeg onder Options de optie Raw Body toe en zet die aan. De node geeft de bytes dan door zoals ze binnenkwamen, in de binaire eigenschap data, naast de geparste JSON in body en de headers in headers.
  4. Publiceer de workflow en kopieer de productie-URL. De test-URL luistert alleen zolang de editor op een testgebeurtenis wacht. Een sync die binnenkomt terwijl er niets luistert krijgt een 404, en de iPhone houdt die payload en de payloads erna in zijn wachtrij tot de URL weer antwoordt.

Tik in de app op Bestemming toevoegen op het tabblad Gezondheid, vul de productie-URL in en tik op Webhook toevoegen. Tik in het paneel dat opent op Genereren onder HMAC-ondertekeningsgeheim, tik op Geheim kopiëren voor de volgende stap en tik daarna op Bewaren.

De handtekening controleren in een Code-node

De iPhone ondertekent precies zoals de Android-app: X-Signature: sha256=<hex>, de HMAC-SHA256 van de ruwe body met je geheim als sleutel. Voeg een Code-node in JavaScript toe, in de modus Run Once for All Items:

const crypto = require('crypto');

// The secret as the app shows it. Use it as text: don't hex-decode it.
const SECRET = 'paste-the-secret-from-the-app';

const item = $input.first();
const raw = await this.helpers.getBinaryDataBuffer(0, 'data');
const expected = Buffer.from(
  'sha256=' + crypto.createHmac('sha256', SECRET).update(raw).digest('hex')
);
const presented = Buffer.from(item.json.headers['x-signature'] || '');
const valid = presented.length === expected.length &&
  crypto.timingSafeEqual(presented, expected);

return [{ json: { valid, payload: valid ? JSON.parse(raw.toString('utf8')) : null } }];
  • De HMAC gaat over raw, de bytes die de app heeft ondertekend. Bereken je hem over een opnieuw geserialiseerde body, dan krijg je een andere string en mislukt de controle.
  • n8n geeft headernamen in kleine letters, dus de header heet x-signature.
  • Iedereen die de workflow kan openen, kan het geheim in de code lezen. De payload-referentie laat dezelfde controle zien met een Crypto-node, die het geheim in een n8n-credential bewaart.

Voeg daarna een If-node toe met één voorwaarde: de boolean {{ $json.valid }} is true.

Antwoord vóór het trage deel

Laat elke tak van de If-node eindigen in een eigen Respond to Webhook-node met Respond With op No Data. Zet onder Options de Response Code op 204 in de true-tak en op 401 in de false-tak. Wat de iPhone met elk antwoord doet:

  • 204. Elke 2xx telt als afgeleverd. De nodes na de Respond to Webhook-node draaien daarna gewoon door, met hetzelfde item.
  • 401. Binnen de sync komt er geen nieuwe poging. De payload blijft in de wachtrij van de iPhone, de payloads erna wachten erachter, en ze gaan de deur uit zodra de geheimen overeenkomen: bij de volgende sync, of met Nu opnieuw proberen.
  • 500. Mislukt de workflow voordat een Respond to Webhook-node draait, dan antwoordt n8n met 500. De iPhone probeert het in totaal 3 keer, met eerst 1 en dan 2 seconden ertussen, en bewaart de payload daarna voor de volgende sync.

Twee dingen zijn anders dan op Android: een payload die je workflow weigert met 400, 413 of 422 wordt één keer per dag opnieuw aangeboden in plaats van bij elke sync, en een payload ouder dan 7 dagen vervalt bij de eerstvolgende aflevering die n8n met een fout beantwoordt.

Van de payload rijen maken

Na de 204 maakt een tweede Code-node van de payload één item per record. Het is dezelfde code als voor Android:

const p = $input.first().json.payload;
if (!p || p.test) return [];

const rows = [];
for (const [type, value] of Object.entries(p)) {
  if (type === 'deleted_records' || !Array.isArray(value)) continue;
  for (const r of value) {
    if (!r || !r.uuid) continue; // daily totals and buckets carry no uuid
    rows.push({ json: {
      type,
      uuid: r.uuid,
      source: r.source ?? null,
      time: r.time ?? r.start_time ?? r.session_end_time ?? null,
      data: r,
    } });
  }
}
return rows;
  • Test versturen en de Testping bij het instellen hebben "test": true en geen records, dus na deze node draait er niets.
  • Op een iPhone is de source van een record de naam die Apple Health geeft aan de app of het apparaat dat het schreef, zoals Alex's Apple Watch, geen pakketnaam. Vaak zit de naam van de eigenaar erin.
  • De uuid van een slaapnacht komt van de vroegste fase en blijft dus gelijk terwijl de nacht groeit, en de upsert hieronder vervangt de nacht als hij langer terugkomt. De fasen van een nacht hebben hun eigen uuid en source in data.
  • Een voedingsmiddel is één nutrition-record met alle voedingsstoffen erin, en de name als de app die heeft meegegeven.
  • Reeksen die je onder Dataresolutie op 1, 5 of 15 minuten of per uur hebt gezet, komen aan als buckets zonder uuid en worden hier overgeslagen. Laat voor deze workflow elk type op elke meting staan; dat is de standaard.

Opslaan in Postgres, ontdubbeld op uuid

Hetzelfde record kan vaker dan één keer aankomen: bij elke backfill, waarmee de app je oude data alsnog verstuurt, en opnieuw vanuit de wachtrij na een aflevering die iOS afbrak. Gebruik type en uuid als sleutel van de tabel, allebei als text:

CREATE TABLE health_records (
  type   text NOT NULL,
  uuid   text NOT NULL,
  source text,
  time   timestamptz,
  data   jsonb NOT NULL,
  PRIMARY KEY (type, uuid)
);

Voeg een Postgres-node toe met de operatie Execute Query:

INSERT INTO health_records (type, uuid, source, time, data)
VALUES ($1, $2, $3, $4::timestamptz, $5::jsonb)
ON CONFLICT (type, uuid) DO UPDATE
SET source = EXCLUDED.source, time = EXCLUDED.time, data = EXCLUDED.data;

Voeg onder Options de optie Query Parameters toe met deze expressie:

{{ [ $json.type, $json.uuid, $json.source, $json.time, JSON.stringify($json.data) ] }}
  • Geef waarden door als Query Parameters, nooit als {{ }} in de SQL zelf. n8n plakt een expressie als platte tekst in de SQL, dus een aanhalingsteken in een waarde, zoals dat in Alex's Apple Watch, maakt de query kapot.
  • De sleutel is type plus uuid, niet alleen uuid: een iPhone stuurt één sample actieve energie onder zowel active_calories als total_calories.
  • Apple Health past een bestaand record niet aan. Een bewerking komt aan als een verwijdering van de oude uuid plus een nieuw record, en dat regelt de volgende stap.

deleted_records toepassen

Een record dat in Apple Health is verwijderd, wordt genoemd in de deleted_records van een latere payload, met zijn type en uuid. Een derde Code-node, ook na de 204:

const p = $input.first().json.payload;
return (p?.deleted_records ?? []).map(d => ({ json: { type: d.type, uuid: d.uuid } }));

Daarna een Postgres-node met Execute Query en de Query Parameters {{ [ $json.type, $json.uuid ] }}:

DELETE FROM health_records
WHERE type = $1 AND (uuid = $2 OR starts_with(uuid, $2 || '#'));

In de uuid's van een iPhone zit nooit een #, dus voor een iPhone telt alleen de eerste helft; de tweede helft is voor hartslag- en huidtemperatuursamples van Android, zodat één workflow beide telefoons aankan. Een verwijderde uuid die je niet hebt verwijdert niets, en dat is precies wat de payloadpagina van de iOS-app vraagt.

Eén geval van de iPhone dekt de query hierboven niet: een verwijdering bij slaap noemt één fase van de nacht, met zijn uuid in stages, niet de nacht zelf. Om die fase uit de opgeslagen nacht te halen, voeg je een tweede Postgres-node toe met dezelfde Query Parameters:

UPDATE health_records
SET data = jsonb_set(data, '{stages}', (
  SELECT coalesce(jsonb_agg(s), '[]'::jsonb)
  FROM jsonb_array_elements(data->'stages') AS s
  WHERE s->>'uuid' IS DISTINCT FROM $2))
WHERE type = 'sleep' AND $1 = 'sleep'
  AND data->'stages' @> jsonb_build_array(jsonb_build_object('uuid', $2::text));

De duration_seconds van de nacht blijft zoals hij is verstuurd. Voor een type dat in deletions_unavailable staat, kan die sync niet instaan: start een backfill vanuit de app om het recht te trekken.

Bouw je de opslag liever niet zelf, dan ontdubbelt en verwijdert de ontvanger van de Life Dashboard-stack op dezelfde manier, met dashboards, een alleen-lezen API en een MCP-server erbovenop.

Liever Google Sheets of Telegram

Eén rij per dag in Google Sheets. Een Code-node na de 204 pakt de dagtotalen, die Apple Health telt zoals de app Gezondheid dat doet, dus een wandeling die de iPhone en de Watch allebei hebben vastgelegd telt één keer:

const p = $input.first().json.payload;
return (p?.daily_totals ?? []).map(d => ({ json: d }));

Daarna een Google Sheets-node met Append or Update Row, een blad met de kolommen date, steps, distance_meters, active_calories en total_calories, en date als kolom om op te matchen. Elke payload bevat vandaag en de twee dagen ervoor, dus de rij van vandaag wordt bij elke sync bijgewerkt. Op een iPhone komt total_calories alleen op dagen met rustenergie, en die legt een iPhone zonder Apple Watch meestal niet vast.

Een Telegram-bericht bij elk nieuw gewicht. Na de node met de records houdt een Filter-node de items over waarbij {{ $json.type }} gelijk is aan weight. Een Remove Duplicates-node met Remove Items Processed in Previous Executions, Keep Items Where op Value Is New en {{ $json.uuid }} als waarde om op te ontdubbelen, voorkomt een tweede bericht als dezelfde weging bij een backfill opnieuw binnenkomt. Daarna een Telegram-node met Send Message en de tekst Weight: {{ $json.data.kilograms }} kg.

Een iPhone en een Android-telefoon in één workflow

  • source op het hoogste niveau is healthkit_ios vanaf een iPhone en health_connect vanaf Android.
  • Hartslagvariabiliteit is SDNN vanaf een iPhone en RMSSD vanaf Android, onder dezelfde sleutel. Sla bij elk record de source van het hoogste niveau op, zodat de twee gescheiden blijven.
  • Het type van een work-out is vanaf een iPhone een naam, zoals running, en vanaf Android het nummer van Health Connect als string, zoals "56".
  • Bij de slaapfasen van een iPhone zit in_bed, de tijd in bed rond de fasen.
  • Schermtijd komt alleen van Android, als een eigen payload.

De stappen voor de records, de upsert en het verwijderen op deze pagina komen uit de workflow in Health Connect naar n8n. De Code-nodes en de SQL zijn hier gecontroleerd tegen een iPhone-payload in Node.js en Postgres, niet in een draaiende n8n waar een iPhone naartoe stuurt. Probeer het dus met Test versturen en Nu synchroniseren voordat je erop vertrouwt.

Beperkingen

  • n8n kan de iPhone niet om een datumbereik vragen. Start een backfill op de iPhone, van 30 dagen tot Alles, met Geschiedenis versturen onder Wat versturen.
  • iOS bepaalt wanneer de app op de achtergrond draait, dus syncs kunnen later komen dan het schema zegt. Voor een exact tijdstip voert een automatisering in Opdrachten Gezondheidsdata synchroniseren uit.
  • Omdat de 204 eerst de deur uit gaat, kunnen twee payloads tegelijk worden opgeslagen. Payloads hebben een sequence die alleen oploopt; gebruik die waar de volgorde ertoe doet, zoals bij daily_totals.

FAQ

Is de workflow anders dan die voor Android?

Alleen in de details op deze pagina. De Webhook-node, de handtekeningcontrole, de antwoorden en de upsert zijn hetzelfde, dus één workflow kan beide telefoons aan. De extra stap is het verwijderen van een slaapfase, dat alleen een iPhone verstuurt.

Werkt dit op n8n Cloud?

Ja. De productie-URL van een gepubliceerde workflow is publiek bereikbaar over HTTPS, en n8n Cloud levert de module crypto aan de Code-node. Zelf gehoste n8n heeft NODE_FUNCTION_ALLOW_BUILTIN=crypto nodig voor dezelfde code.

Waarom mislukt de handtekeningcontrole bij elk verzoek?

Meestal is het een van deze drie: Raw Body staat uit, dus er is geen binaire data om te hashen; de HMAC gaat over de geparste body in plaats van de ruwe bytes; of het geheim in n8n is een ander dan dat in de app. Kopieer het geheim opnieuw en gebruik het als platte tekst.

Komt data van de Apple Watch ook in n8n?

Ja. Het horloge schrijft naar Apple Health op de iPhone, en de app stuurt de data door zodra het horloge met de iPhone heeft gesynchroniseerd. Apple Watch in Home Assistant zet op een rij wat een horloge doorgaans vastlegt.

Kan ik een payload bekijken voordat ik de workflow bouw?

Ja. Voorbeeld van payload onder Wat versturen in de app toont de laatste 7 dagen als payload. In n8n laat de test-URL met Listen for Test Event een echt verzoek zien in de editor.
