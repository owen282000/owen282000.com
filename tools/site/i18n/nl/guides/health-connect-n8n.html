Hoe krijg ik Health Connect-data in n8n?

Installeer Life Dashboard Companion, een open-source Android-app, en vul de productie-URL van een Webhook-node in n8n in als webhook. Zet in n8n de optie Raw Body van de Webhook-node aan, controleer de HMAC in X-Signature in een Code-node, antwoord 204 met een Respond to Webhook-node en sla daarna elke meting op met type en uuid als sleutel. Data uit Samsung Health, Garmin Connect, Google Health, Oura en Withings bereikt n8n op deze manier, omdat die apps hun data op de telefoon naar Health Connect schrijven.

De iPhone-app stuurt Apple Health-data in hetzelfde formaat, dus één workflow kan beide telefoons aan. Deze pagina gaat over de kant van n8n. De payload zelf, nieuwe pogingen en de wachtrij staan in Health Connect naar een webhook.

Wat je nodig hebt

  • Life Dashboard Companion voor Android op Android 9 of nieuwer met Health Connect. {{status:android}}
  • Of de iPhone-app op iOS 17 of nieuwer. {{status:ios}}
  • n8n, in n8n Cloud of zelf gehost, bereikbaar vanaf de telefoon. Gebruik HTTPS. Voor onversleutelde HTTP in je eigen netwerk zet je in de Android-app Onversleutelde HTTP-webhooks toestaan aan onder Meer > Geavanceerd. De iPhone-app staat onversleutelde HTTP alleen toe naar een IP-adres, een .local-naam of een naam zonder punt.
  • Ruimte voor grote verzoeken. Sta minstens 10 MB per verzoek toe. n8n accepteert standaard tot 16 MB, maar een reverse proxy ervoor moet dat ook toestaan: nginx staat standaard 1 MB toe.
  • De module crypto in de Code-node. n8n Cloud levert die mee. Stel bij zelf gehoste n8n NODE_FUNCTION_ALLOW_BUILTIN=crypto in, op de task runner als je die gebruikt.

De workflow in één oogopslag

Webhook (POST, Raw Body)
  -> Code: check signature
  -> If: valid is true
       true  -> Respond to Webhook (204)
                  -> Code: records    -> Postgres: upsert
                  -> Code: deletions  -> Postgres: delete
       false -> Respond to Webhook (401)

Het antwoord gaat de deur uit vóór het databasewerk, omdat de app hooguit 10 seconden op een antwoord wacht.

De Webhook-node instellen

  1. Voeg een Webhook-node toe. Zet HTTP Method op POST en kies een Path, bijvoorbeeld life-dashboard.
  2. Zet Respond op Using 'Respond to Webhook' Node. Met Immediately antwoordt n8n 200 voordat de controle van de handtekening draait, waardoor een payload met een verkeerde handtekening toch als afgeleverd telt.
  3. Voeg onder Options de optie Raw Body toe en zet haar aan. De node geeft de bytes dan zoals ze binnenkwamen door in de binaire eigenschap data, naast de geparste JSON in body en de headers in headers.
  4. Publiceer de workflow en kopieer de productie-URL. De test-URL luistert alleen terwijl de editor op een testgebeurtenis wacht, en de productie-URL werkt alleen zolang de workflow gepubliceerd is. Een sync op een ander moment krijgt een 404, en de app bewaart die payload en de payloads erna tot de URL weer antwoordt.

Tik in de app op het tabblad Gezondheid op Bestemming toevoegen (is er nog niets ingesteld: Je eigen server gebruiken), plak de productie-URL onder Webhook-URL en tik op Webhook toevoegen. Tik op de pagina die opent op Genereren onder HMAC-ondertekeningssleutel (optioneel), kopieer het geheim met Geheim kopiëren voor de volgende stap en tik op Bewaren.

De handtekening controleren in een Code-node

Elk verzoek draagt X-Signature: sha256=<hex>, de HMAC-SHA256 van de ruwe body met je geheim als sleutel. Voeg een Code-node in JavaScript toe, in de modus Run Once for All Items:

const crypto = require('crypto');

// The secret as the app shows it. Use it as text: don't hex-decode it.
const SECRET = 'paste-the-secret-from-the-app';

const item = $input.first();
const raw = await this.helpers.getBinaryDataBuffer(0, 'data');
const expected = Buffer.from(
  'sha256=' + crypto.createHmac('sha256', SECRET).update(raw).digest('hex')
);
const presented = Buffer.from(item.json.headers['x-signature'] || '');
const valid = presented.length === expected.length &&
  crypto.timingSafeEqual(presented, expected);

return [{ json: { valid, payload: valid ? JSON.parse(raw.toString('utf8')) : null } }];
  • De HMAC loopt over raw, de bytes die de app heeft ondertekend. Bereken je hem over body die opnieuw is geserialiseerd, dan krijg je een andere string en mislukt de controle.
  • n8n geeft headernamen in kleine letters, dus de header heet x-signature.
  • timingSafeEqual vergelijkt in constante tijd en geeft een fout bij invoer van verschillende lengte, dus de lengtecontrole komt eerst.
  • Iedereen die de workflow kan openen, kan het geheim in de code lezen. Als dat een bezwaar is: de payload-referentie toont dezelfde controle met een Crypto-node, die het geheim in een n8n-credential bewaart.

Voeg daarna een If-node toe met één voorwaarde: de boolean {{ $json.valid }} is true.

Antwoorden vóór het trage deel

Laat elke tak van de If-node eindigen in een eigen Respond to Webhook-node met Respond With op No Data. Zet onder Options de Response Code op 204 in de true-tak en op 401 in de false-tak.

  • 204. De app telt elke 2xx als afgeleverd. De nodes na de Respond to Webhook-node draaien nog steeds, met hetzelfde item.
  • 401. De app probeert het niet opnieuw. Hij bewaart de payload, en de payloads erna, in zijn wachtrij en levert ze af zodra de geheimen overeenkomen.
  • 500. Als de workflow mislukt voordat een Respond to Webhook-node draait, antwoordt n8n 500. De app probeert het in totaal 3 keer en bewaart de payload daarna voor de volgende sync.

Van de payload rijen maken

Na de 204 maakt een tweede Code-node van de payload één item per meting:

const p = $input.first().json.payload;
if (!p || p.test) return [];

const rows = [];
for (const [type, value] of Object.entries(p)) {
  if (type === 'deleted_records' || !Array.isArray(value)) continue;
  for (const r of value) {
    if (!r || !r.uuid) continue; // daily totals and buckets carry no uuid
    rows.push({ json: {
      type,
      uuid: r.uuid,
      source: r.source ?? null,
      time: r.time ?? r.start_time ?? r.session_end_time ?? null,
      data: r,
    } });
  }
}
return rows;

Test versturen vanuit de app levert geen rijen op, dus na deze node draait er dan niets. Reeksen die je onder Dataresolutie op 1, 5 of 15 minuten of per uur hebt gezet, komen binnen als buckets zonder uuid en worden hier overgeslagen: laat Dataresolutie voor deze workflow op elke meting staan, of bewaar buckets in een eigen tabel met de reeks en bucket_start als sleutel.

Opslaan in Postgres, ontdubbeld op uuid

Dezelfde meting kan meer dan eens binnenkomen: na een nieuwe poging, wanneer de bron de meting bewerkt, en in elke backfill, waarmee de app je oude data alsnog verstuurt. Geef de tabel type en uuid als sleutel, allebei als text:

CREATE TABLE health_records (
  type   text NOT NULL,
  uuid   text NOT NULL,
  source text,
  time   timestamptz,
  data   jsonb NOT NULL,
  PRIMARY KEY (type, uuid)
);

Voeg een Postgres-node toe met de operatie Execute Query:

INSERT INTO health_records (type, uuid, source, time, data)
VALUES ($1, $2, $3, $4::timestamptz, $5::jsonb)
ON CONFLICT (type, uuid) DO UPDATE
SET source = EXCLUDED.source, time = EXCLUDED.time, data = EXCLUDED.data;

Voeg onder Options de optie Query Parameters toe met deze expressie:

{{ [ $json.type, $json.uuid, $json.source, $json.time, JSON.stringify($json.data) ] }}
  • Geef waarden door als Query Parameters, nooit als {{ }} in de SQL. n8n plakt een expressie als platte tekst in de SQL, dus een aanhalingsteken in een waarde breekt de query.
  • De sleutel is type plus uuid, niet alleen uuid. Metingen van hartslag en huidtemperatuur hebben een uuid als <record id>#<epoch ms>, en een iPhone stuurt één meting van actieve energie onder zowel active_calories als total_calories.
  • Vanaf Android komt een bewerkte meting binnen met dezelfde uuid en nieuwe waarden, en de upsert vervangt de oude rij. Apple Health bewerkt niet ter plekke: een bewerking komt binnen als een verwijdering en een nieuwe meting.

deleted_records verwerken

Een meting die in Health Connect of Apple Health is verwijderd, staat in deleted_records van een latere payload, met type en uuid. Een derde Code-node, ook na de 204:

const p = $input.first().json.payload;
return (p?.deleted_records ?? []).map(d => ({ json: { type: d.type, uuid: d.uuid } }));

Daarna een Postgres-node met Execute Query en de Query Parameters {{ [ $json.type, $json.uuid ] }}:

DELETE FROM health_records
WHERE type = $1 AND (uuid = $2 OR starts_with(uuid, $2 || '#'));

De tweede helft verwijdert de metingen van een hartslag- of huidtemperatuurrecord van Android. Vanaf een iPhone noemt een slaapverwijdering één fase van de nacht, niet de nacht zelf, dus deze query laat de nacht staan. Voor een type dat in deletions_unavailable staat, kan de telefoon bij die sync niet instaan: start een backfill vanuit de app om het recht te trekken.

Staan de metingen eenmaal in Postgres, dan kan een model ze lezen via een alleen-lezen rol en een MCP-server: Health Connect-data via MCP beschrijft die route. Bouw je de opslag liever niet zelf, dan ontdubbelt en verwijdert de ontvanger van de Life Dashboard-stack op dezelfde manier, met dashboards, een alleen-lezen API en een MCP-server erbovenop.

Of Google Sheets of Telegram

Eén rij per dag in Google Sheets. Een Code-node na de 204 pakt de dagtotalen, die een wandeling één keer tellen, ook als telefoon en horloge die allebei hebben geregistreerd:

const p = $input.first().json.payload;
return (p?.daily_totals ?? []).map(d => ({ json: d }));

Daarna een Google Sheets-node met Append or Update Row, een blad met de kolommen date, steps, distance_meters, active_calories en total_calories, en date als de kolom om op te matchen. De rij van vandaag is een lopend totaal en wordt bij elke sync bijgewerkt. Een veld ontbreekt op een dag zonder data voor dat type.

Een Telegram-bericht bij elk nieuw gewicht. Na de node met metingen houdt een Filter-node de items over waarbij {{ $json.type }} gelijk is aan weight. Een Remove Duplicates-node met Remove Items Processed in Previous Executions, Keep Items Where op Value Is New en {{ $json.uuid }} als de waarde om op te ontdubbelen voorkomt een tweede bericht wanneer dezelfde weging in een backfill opnieuw langskomt. Daarna een Telegram-node met Send Message en de tekst Weight: {{ $json.data.kilograms }} kg.

Samsung Health, Garmin en Apple Health in één workflow

  • De source van elke meting is de pakketnaam van de app die de meting schreef, zoals com.sec.android.app.shealth voor Samsung Health, com.garmin.android.apps.connectmobile voor Garmin Connect of com.fitbit.FitbitMobile voor Google Health. Filter daarop om één merk apart te routeren.
  • De source op het hoogste niveau is health_connect vanaf Android en healthkit_ios vanaf een iPhone. Op een iPhone is de source van een meting de naam die Apple Health aan de app of het apparaat geeft.
  • Hartslagvariabiliteit is RMSSD vanaf Android en SDNN vanaf een iPhone, onder dezelfde sleutel. Sturen beide telefoons naar deze workflow, sla dan bij elke meting de source van het hoogste niveau op, zodat de twee uit elkaar blijven.
  • Welke types elke app schrijft, en welke hij voor zichzelf houdt, staat in Health Connect-datatypes, app voor app.

Beperkingen

  • n8n kan de telefoon niet om een datumbereik vragen. Start een backfill op de telefoon, van 30 dagen tot Alles, onder Geschiedenis versturen, in Wat versturen op het tabblad Gezondheid.
  • Omdat de 204 eerst de deur uit gaat, kunnen twee payloads tegelijk worden opgeslagen. Payloads hebben ook een sequence die alleen oploopt: Health Connect naar een webhook legt uit hoe je die gebruikt wanneer de volgorde ertoe doet, zoals bij daily_totals.
  • Schermtijd komt binnen als eigen payload met "source": "screen_time", vanaf de URL's op het tabblad Schermtijd. Die heeft geen uuid's per meting, dus de node met metingen hierboven slaat die payload over.

FAQ

Werkt dit op n8n Cloud?

Ja. De productie-URL van een gepubliceerde workflow is publiek HTTPS, en n8n Cloud levert de module crypto aan de Code-node. Zelf gehoste n8n heeft voor dezelfde code NODE_FUNCTION_ALLOW_BUILTIN=crypto nodig.

Waarom mislukt de controle van de handtekening bij elk verzoek?

Meestal is het een van deze drie dingen: Raw Body staat uit, dus er is geen binaire data om te hashen; de HMAC loopt over de geparste body in plaats van over de ruwe bytes; of het geheim in n8n wijkt af van dat in de app. Kopieer het geheim opnieuw en gebruik het als platte tekst.

Kan ik de handtekening overslaan?

Ja. Zonder geheim stuurt de app geen X-Signature. Bescherm de URL dan op een andere manier, bijvoorbeeld met Header Auth op de Webhook-node en dezelfde header onder Headers op de pagina van het adres in de app.

Komt data uit Samsung Health in n8n aan?

Ja, zodra Samsung Health die data met Health Connect deelt: stappen, work-outs, slaap met fasen, hartslag, bloeddruk, gewicht en meer. Samsung Health deelt hartslagvariabiliteit en hartslag in rust niet met Health Connect, dus die komen niet aan.

Kan ik een payload zien voordat ik de workflow bouw?

Ja. Voorbeeld van payload onder Wat versturen op het tabblad Gezondheid van de app laat zien wat de volgende sync zou versturen. In n8n toont de test-URL met Listen for Test Event een echt verzoek in de editor.
